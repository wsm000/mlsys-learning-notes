# Task0–Task5 整体学习心得：从一条公式，到一套判断标准

> 课程⑧《AI Agent：从入门到工程实践》Chapter 1–5、10。
> 跨度：2026-10-12 至 2026-10-29。环境：vm-60（RTX 4090 D / Qwen3-0.6B / Ollama）与本机 Windows 双轨，
> 模型涉及 MiMo-V2.6-Flash、Qwen3-0.6B、gpt-5.6-sol（本机 8789 端口 Responses API 代理）。
> 本文不是各章摘要的拼接，而是想回答一个问题：**这六章学完之后，我看 Agent 的方式发生了什么变化。**

---

## 一、那条公式我读错了三次

课程主线是 **Agent = LLM + Context + Tools**。

Task0 第一次见到它时，我把它当成一张成分表：LLM 是大脑，Context 是记忆，Tools 是手脚。
三者备齐，Agent 就能干活。那一次的真实对照很干脆：让模型算 `(125 + 375) × 8`，
正常回传工具结果的一组用了 2 轮、1 次调用；把工具结果藏起来的一组用了 4 轮、5 次调用。
**两组最终都答对了 4000。**

如果我停在成分表，这个实验只会让我得出一个平淡的结论：有反馈更好一点。
真正让我停下来的是那个刺眼的对比——答案一样，路径差了一倍多。
于是公式在我手里变了第一次：

> **LLM 是通用能力，Context 决定这一次能依据什么作判断，Tools 把判断变成外部状态的变化。**

三者不是并列的零件，而是一条运转的回路。Context 不是聊天记录的备份，
它是模型判断「我已经做过什么、刚才得到了什么」的唯一依据。

Task1 把这条回路拆到了 token 一级。工作台有固定长度，模型按 token 读输入，
上传一个文件不等于它的每一段都值得一直摆在工作台上。
那次压缩实验我至今记得很清楚：14,897 个 token 的资料快照，
任务感知摘要只保留 314 个，五项事实问答仍然全部匹配——**2.11%**。
我原来的直觉是「信息越多判断越准」，这个数字直接反驳了它：
判断质量不取决于桌上堆了多少，而桌上放的是不是下一步要用的那几个路口。

到 Task5，这条公式被我改成了第三次，也是最重要的一次：

> **Agent 的价值不在于它能做什么，而在于它能否知道做完之后发生了什么。**

这一句不是从某一章读来的，是六章实验一次次把我按到这个结论上的。

## 二、六个任务，各自改变了我哪一层理解

### Task0：分清「程序知道」和「模型知道」

最反直觉的一个发现：隐藏工具结果的那一组，**本地记录里是有 4000 的**。
程序算对了，存下了，只是没送进下一轮模型输入。
于是模型反复调计算器，还把表达式改写成 `500 * 8` 再算一次。

这件事我后来在各种场合反复遇到：工具执行成功、结果写进了日志、文件落盘了——
都和「模型能依据它继续判断」是三件不同的事。
Task0 给我的不是某个知识点，是**第一个可以把关的提问方式**：
这个结果，模型这一轮真的看见了吗？

### Task1：上下文工程是持续的信息组织，不是写提示词

学这一章之前，我会把 Agent 的表现归结到模型大小或提示词写法。
六组消融把这件事打碎了：表达风格从夸张到口语，成绩都是 8/10；
而把业务规则的组织方式打乱，掉到 5/10；把工具参数描述清空，6/10。
**同样是十个字以内的改动，改风格没用，改组织方式和改含义就有用。**

注意力矩阵那三张图则让我第一次「看见」上下文：第 0、13、27 层，
首 token 获得的平均注意力从 14.7% 涨到 73.9%，再到 83.1%。
抽象的上下文变成了可测量的 token 间权重。

但这一章对我最大的影响是那句我后来当成最低记录来用的六行：

```text
目标：要完成什么
约束：必须遵守什么
已做：采取了哪些动作
证据：得到了什么结果，原文在哪里
状态：哪些结论已确认，还需要解决什么
下一步：基于上述信息继续行动
```

它后来在 Task3 的子 Agent 交接、Task4 的长任务断点、Task5 的消息信封里反复出现。
我慢慢意识到，这六行不是某一种技术的格式，而是**任何需要接续的工作都逃不掉的字段**。

### Task2：记忆和知识的更新规则不能混为一谈

十二项机制实验里，我最珍视的不是 240/240，而是那几个「没证明」的结论。
3-8 让模型自己决定搜还是不搜，控制器追错了方向还重复搜索——机制跑通了，但没有质量收益。
3-9 和 3-11 更直接：正确证据进了上下文，模型照样答错。

这三个负结果合起来给了我一个比任何正结果都有用的东西：
**检索做对，只是让正确的证据出现在候选里；它不保证模型选中它，更不保证结论正确。**
后来我把这套排查顺序当成了检查清单：

1. 原文是否包含所需事实？
2. 切分、表示、更新是否丢掉主体、条件或时间？
3. 正确证据是否进入候选、最终上下文？
4. 相关记忆是否过期、冲突或被不可信指令污染？
5. 输出采用了哪条来源，引用是否支持结论？

五句话对应五种不同的失败。混成一句「效果不好」，就永远不知道该修哪一层。

另外一条是：用户记忆记录个人背景与状态，知识库提供领域资料，
两者可以共享切分、索引、检索技术，但**更新规则、适用范围和失效判断不能混**。
这条在 Task5 划分子 Agent 的写范围与共享空间时派上了用场：各自私有的 scratchpad、
多方读写的共享区、全局只读的上游快照，靠的正是把「谁能改、改了什么算数」分开定义。

### Task3：一次成功返回，能证明的事情比看起来少

这一章有一个我特别喜欢的小实验：输入 `apple banana apple`，真值是 2。
两个程序都正常退出、退出码都是 0、都通过工具自带的 verification，
一个打印 3，一个打印 2。**只有加入任务专用的验证，才能区分它们。**

它把「成功」拆成了三个必须分别回答的问题：
请求是否获得有效响应？操作是否完成？任务目标是否达到？
这三个问题可能得到不同答案，而我以前的默认动作是把它们合并成一个绿色的勾。

五类工具的划分（感知、执行、协作、事件触发、用户沟通）也改变了我的设计习惯。
它关心的不是代码是否运行、是否经过网络，而是**一次交互承担什么作用**。
同一个 `search_logs(query)` 会运行搜索程序，但它承担的是感知。
分类的价值在于提醒我：读取要控制信息量，写入要管理副作用，委派要明确责任与验收。

协作工具那一节我印象最深的一句话是：**委派时传递的不只是任务，还有验收责任。**
「词频已经检查，结果正确」是一句无法复核的报告；有用的报告会说明输入文件版本、
分词规则、计算结果和对应位置。这句话我在 Task5 当 Manager 时几乎是一字不差地执行了。

### Task4：代码元能力，以及「修订是一层新证据」

折扣公式那行 `return sum(prices) * discount` 是个漂亮的入口。
模型知道答案（把 discount 换成 1 - discount），但答案在纸上成立，不等于文件被改、
不等于调用方执行它、不等于业务结果对。

NaN 那个实验让我印象最深：两条看起来等价的区间判断，
`if discount < 0 or discount > 1` 和 `if not (0 <= discount <= 1)`，
在普通实数上完全等价，遇到 NaN 一个放行一个拒绝。
**没有靠解释宣布胜负，是靠执行三轮、看测试从失败变通过再变失败。**

销售报告那个实验给了我一个至今仍在用的概念：那 60 元。
C002 金额 60 元但地区为空。删掉它丢钱，猜一个地区制造事实，
把「待确认」写成真实业务地区混淆分类。最后它被单独保留成一行「地区待确认」，
总额 500 元守恒，归属不确定也同时被表达。程序成功退出，业务验收仍然是「草稿，未完成」。

**这两个状态不能合并成一个绿色的成功。**

还有修订层的设计：确认信息写进独立文件，记录源文件、源版本哈希、原字段值、新字段值和依据；
应用前要求源版本匹配、目标只出现一次、原字段值一致。原始 CSV 不变，草稿也保留。
我从中读到的不是技术，是一种态度：**新知识不应该悄悄改写过去，它应该是一层可追溯的增量。**

### Task5：多 Agent 的第一判据，和一次自我审查的有害实证

Chapter 10 我先纠正了题面一个前提：上游 `chapter10/` 下并没有
Planner→Researcher→Executor→Reviewer 这种通用教程目录，而是七个并列的实验项目。
这条链路我按「典型工作流」讲，并如实注明了。

这一章我做了三组实验，最重要的结论来自表 10-1 那条判据的复现：
**协作是否引入单个 Agent 生成时拿不到的新信息。**

补足样本量之后（28 对扩到 113 对，McNemar p=0.0117），数字是显著的，
但机制和我预期的完全不同：identity-constant 族上生成者 100% 正确，
无证据的审查者 B1 只有 55.6%——**它把 18 个里的 8 个正确答案改错了**。
有执行证据的 B2 保持 94.4%。

所以显著差异的主导机制不是「执行反馈让审查者能修正错误」，
而是「**无外部证据的自我审查有害**」。后者当然也发生了，但不是主要的那个。
这和 Huang 等 ICLR 2024 的结论一致，也和书里表格的另一行对应。

另一个反直觉的实测是加速比：并行编排的机制全部通过（一次结算、一次终止广播、ack 对账、零泄漏），
但真实条件下并行只比串行快 1.009×，纯调度桩对照是 8.003×，真实站点直连甚至只有 0.6× 和 0.103×。
**并行掉的是最便宜的那段（抓取 0.02 秒），等的是最贵的那段（模型调用 5–6 秒）。**
这件事我以前是想当然的。

## 三、六章之后，我稳定下来的四条判断

这些不是某一章的知识点，是六个任务反复把我按上去之后，我发现自己开始默认遵守的东西。

### 1. 「完成」只是一句宣称，不是证明

Task3 的两个程序都退出码 0；Task4 的程序成功退出而业务状态是草稿；
Task5 的 Agent 宣称完成而验证没跑。三种形态，同一个根源：
**在验证之前，完成只是模型的一句话。**

由此我得到一条操作规则：任何「完成」都要配一个能回答「凭什么」的证据，
而且证据要能区分正确实现和错误实现。一个永远返回成功的检查器，对纠错毫无帮助。

### 2. 三个问题必须分开回答

请求是否获得有效响应？操作是否完成？任务目标是否达到？

这条来自 Task3，但它在每一章都换了面孔出现：
Task0 是「程序算对了」和「模型看见了」；
Task1 是「资料在磁盘上」和「资料进了上下文」；
Task2 是「证据在候选里」和「模型选中了它」；
Task4 是「测试通过」和「业务结果正确」。
我以前的习惯是把它们合并成一个判断，现在会条件反射式地拆开。

### 3. 瓶颈在验证器，不在模型

这是 Loop 工程的核心共识，也是我这次体会最深的一条。
Task5 的教训最直接：我三次在中期统计里把「没有产出答案」当成「答错」，
每次都是靠回头翻原始 `raw_response` 才发现——
那些记录的 `status=incomplete`，输出预算被推理吃光，根本没有答案文本。
**派生指标和原始记录一旦脱钩，它就会在你看不见的地方改写结论。**

所以现在的顺序是：先确认口径（什么算一条有效样本），再跑实验，最后才看数字。
反过来做，数字漂亮但不可信。

### 4. 来源和权限，与内容同样重要

Task1 的实验 2-5 把「资料来自哪里」变成了具体问题：网页里的文字即使写成命令，
也仍然是被阅读的内容。Task3 说得更直接：**能读到，不等于有权执行。**
Task4 的修订层用文件哈希拒绝过期依据——哈希能检查版本，不能证明确认内容真实。

合起来我得到的不是一条技术，是一种提问习惯：这条信息能作为哪一种依据？

## 四、方法论上，我踩过的坑比学到的知识点更值钱

### 坑一：把口径当成细节，结果口径就是结论

Task5 的审查证据实验，我先后修掉两个评分缺陷才拿到可信数字。
第一个：`status=incomplete` 的记录被字面匹配当成答错，
修补前 B1 有 17 条、B2 有 0 条——**这是对 B1 的系统性歧视，不是模型差异**。
第二个：筛选阶段把「真值为空（程序抛异常）」当成生成者错误，
高估了模型出错的频率，也高估了加样本的必要性。

修完之后 p 从 0.500 变成 0.0117。**同一个数据集，口径不同，结论相反。**

### 坑二：为了「看起来完整」而补一个漂亮的运行

Task5 的并行实验，一次 15 路完整合并运行跑了 60 多分钟没收尾。
我最后交付的是已完成且可复核的 run1 加两次级联加桩对照，没有编造一次全量运行。
Task4 的幂等、事务、邮件接口讨论也明确标注为设计分析、未做端到端验证。

**未完成就是未完成，写成已验证是最贵的错误。**

### 坑三：相信「全部通过」的口头汇报

Task5 我作为 Manager 派了三个子 Agent。runner 汇报说 16 个 pytest 全绿，
我复跑是 15 passed / 1 failed。它不是故意造假，是交付前又改了一版代码而没重跑。
**最后一句话之后还有一次改动，是多 Agent 系统里最常见的掉链子点。**

由此我给自己定了一条：验收必须自己跑一遍，包括重算笔记里的每一个数字。

### 坑四：把工具的静默失败当成模型的失败

Task5 实验 A 的 A1 组三次全挂，根因是我自己写的工具缺陷：
`period` 大小写敏感，加上 `list_dir` 越界。它调了数据工具但没读到数据，后续步骤也没人发现。
我保留了这个失败没有修饰，因为它恰好说明了单 Agent 的一种真实死法：
**工具静默失败会被埋在长轨迹里，而多阶段分工至少让某一步专门负责核对。**

## 五、如果只留一句话

六章之前，我会问：这个 Agent 能不能做到？
六章之后，我问的是四个问题：

```text
它做到了什么？（可验证的事实）
它凭什么这么说？（证据能否区分对错）
这个结论的边界在哪里？（样本、条件、口径）
还有什么是没做到的？
```

课程那句 **Agent = LLM + Context + Tools**，我现在会读成一条运转的回路：
模型根据眼前的信息选择行动，工具带来新的观察，上下文工程把这些观察整理成可以继续工作的依据。
而**验证决定这个回路是在积累进展，还是在把错误越滚越大**。

那张写着 4000 的纸条，从 Task0 留在另一个房间，到 Task5 被写进消息信封、附上哈希、可被独立复核——
这条线索大概就是我这两周真正学到的东西。

# 3-9：从历次会话中找回用户记忆

## 要实现什么机制？

像从多次巡蜂记录里找出“哪箱蜂需要处理”，本实验把检索对象由共享手册换成用户的原始会话历史。目标是建立可搜索、可追溯的长期记忆入口，而不是把全部历史塞进每次对话。

```text
按用户划分会话历史
      ↓
固定对话窗口切块，保留会话ID、时间、角色与位置
      ↓
BM25索引＋真实Embedding向量索引
      ↓
search_user_memory(用户范围, 查询)
      ↓
必要时继续搜索 → 组装历史证据 → 回答并澄清
```

与3-1／3-2不同：前者主要保留被提炼和改写的记忆；本项保留可检索的原始会话片段。找到的历史事实还需要核对主体、时间和状态。

## 实际输入与范围

本轮使用教程固定版本dbc046eb896ac4e39aa19c7774c8bf49583b89a6中的两个原始layer2用例：

| 用例 | 历史会话 | 窗口块 | 要观察什么 |
|---|---:|---:|---|
| 多辆车 | 2 | 33 | 找齐Honda与Tesla，并区分预约和仅讨论 |
| 多次转账修改 | 3 | 36 | 区分旧金额、修改与最终有效状态 |

每块最多4轮用户—助手对话，相邻块重叠1轮，不跨会话拼接；尾部可不足4轮。每个块保留原始消息、会话编号、时间和轮次范围。

实际使用BGE-small-zh-v1.5向量、从零BM25、RRF融合和本地Qwen3-0.6B。每个用例独立建索引，模拟用户范围隔离；这不是生产身份认证测试。Embedding输入最长512 tokens，原始块完整保留在结果中。参考答案和评审标准没有进入索引或模型输入。

等价教学范围为2个官方用例，不是原60例全量campaign，也没有外部模型评分。所有金额、账户和人物都是原基准中的虚构资料。

## 对比了哪些路径？

1. **一次检索：**原问题检索Top-3，再回答。
2. **模型控制追加检索：**模型选择search或finish，最多总计3次搜索，程序拦截重复查询。
3. **会话覆盖对照：**人工规定的装配策略，在返回候选中按会话各取最多2块，新会话优先展示。
4. **相邻块对照：**对第3条的命中块，在同一会话内扩展±1块，去重并按会话时间及轮次组织。

后两条不是模型自主决策。覆盖对照扩大了上下文，并改变了呈现顺序，不能单独归因于“时间排序”。第3条从稠密与稀疏各前10候选的并集中选择，不能保证全库所有会话都进入候选；本次实际覆盖了两个用例的全部会话。

## 一、多个对象：搜到一辆车，不代表用户只有一辆车

原问题询问“我的车”有哪些已安排的服务。教材历史同时包含2019 Honda Accord与2023 Tesla Model 3：Honda有预约；Tesla曾讨论轮胎换位，但未完成预约，应分别说明并询问用户指哪辆车。

Top-3返回：

```text
H18：第二次会话，确认Honda与保养信息
H20：第二次会话，提供周五和周六两个可选时间
H1 ：第一次会话，明确提到新买的Tesla Model 3
```

模型回答只说Honda，还把两个可选时段一起写成预约信息。Tesla身份已在上下文中，但没被纳入回答；其服务状态对应的H27/H28也未进入此Top-3。

模型控制器输出finish，没有继续查另一辆车。会话覆盖对照让答案提到了Tesla，却混入保险与拖车资料，仍未完成清楚的预约状态区分与澄清。相邻扩展也没取到Tesla服务状态所在的远处窗口。

这个例子同时存在两层问题：**需要的历史没有取齐；已取到的多实体信息也没有被充分使用。** “覆盖两次会话”不能替代“覆盖两辆车的相关事实”。

## 二、时间冲突：语义最相关，不等于最新有效

原始历史的修改过程为：

```text
9月15日：85,000，编号WT-89045
9月25日：改为100,000，编号WT-89067
9月26日：改为95,000，编号WT-89089，旧编号失效
```

这不是现实银行状态说明，而是此虚构用例内部的事件时间线。

### 第一阶段：最终修改根本没进上下文

Top-3取到9月15日的H1、H5及9月25日的H13，没取到9月26日。回答使用85,000，控制器仍输出finish。

这里应先修检索与证据完整性，不能要求回答模型凭空知道最新95,000。

### 第二阶段：覆盖最新会话，仍没覆盖最终金额

会话覆盖对照取到了9月26日的H27和H32：

- H27仍在讨论“保留100,000还是改回85,000？”
- H32说明旧编号失效，但这块没有95,000的最终金额。

回答变成100,000，仍不正确。**命中最新会话，不等于命中该会话的最终决定。** 同一会话内部也有“讨论→修改→确认”的顺序。

### 第三阶段：相邻扩展取到正确证据，模型仍用错

将H32扩展到相邻H31后，上下文明确含有：

```text
[H31] timestamp=2024-09-26 16:00:00
ASSISTANT: Updated: $95,000 to Chase on October 1st.
ASSISTANT: New reference is WT-89089.
ASSISTANT: Previous references are automatically superseded.
           Only WT-89089 is active.
```

但本地模型的最终回答把金额写成100,000，同时采用WT-89089。它将旧金额与新编号拼成了一个不受最新来源支持的组合。

此时诊断已改变：正确金额明确进入了实际模型输入，不能继续把全部问题归为检索遗漏。需要检查生成对事件顺序、字段来源和状态的使用。继续增加Top-k未必解决，还可能引入更多旧版本干扰。

## 三、怎样看中间结果才不会误判？

| 检查问题 | 本轮证据 |
|---|---|
| 相关历史入库了吗？ | 69个原始会话窗口均已保存并编码 |
| 正确片段被检索了吗？ | 转账Top-3未取到最新会话 |
| 最新会话是否包含最终事实？ | H27/H32仍缺最终金额 |
| 正确证据进入最终输入了吗？ | 相邻扩展的H31含95,000与WT-89089 |
| 模型真正采用了什么？ | 回答用了100,000与WT-89089，混合状态 |

时间戳是解释线索，不是自动覆盖命令。新会话可能只更新某个字段；旧会话仍可提供未改变的收款账户等信息。应按同一对象、同一字段及明确修改关系判断，而非简单删除所有旧记录。

## 运行完成不等于回答通过

本轮真实完成切块、索引、检索、控制器和回答。控制器在两个用例都提前finish，没有追加搜索；最终回答存在漏实体、混淆候选时段、误用旧金额和引用不完整等失败，全部保留。结果中的字符串出现检查只用于定位，不能冒充语义评分或官方通过率。

下一项3-10处理另一类问题：一个窗口脱离整段会话后，主体或事件背景不清楚，怎样在建索引前为它补充来源背景。

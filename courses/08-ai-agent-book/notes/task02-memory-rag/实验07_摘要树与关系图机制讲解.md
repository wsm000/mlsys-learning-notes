# 3-7：把档案整理成摘要树，或连接成关系图

## 本实验想实现什么机制？

像整理两处蜂场的巡检档案：摘要树先让你看到“各蜂场有哪些管理事项”，需要细节时回到原始记录；关系图则让你沿着“蜂场管理谁、蜂群有什么问题、问题参考哪本手册”追踪证据。

本轮在vm-60用本地Qwen3-0.6B实际生成摘要和关系，再查询。8条自建档案、2个蜂场，保留全部输入与模型原始输出。属于机制等价教学实现：替代官方Intel技术文档对照；摘要树按已知蜂场元数据分组，没有自动聚类和语义导航；关系图没有完整GraphRAG的社区发现与社区摘要。不能据此宣称完成官方原样基准。

## 同一批原始资料

```text
C1 青禾蜂场位于河谷镇。青禾蜂场管理蜂群A。
C2 蜂群A发现蜂螨。蜂螨防治参考手册M。
C3 手册M要求先监测蜂螨数量，再决定防治措施。
C4 河谷镇冬季寒冷。青禾蜂场冬季管理包括保温和饲料检查。

C5～C8：白石蜂场、蜂群B、饲料不足、手册N与防风饮水事项。
```

问题一是概览：“青禾蜂场主要需要关注哪些管理事项？”

问题二要跨段连接：“青禾蜂场管理的蜂群遇到了什么问题，应参考哪本手册，手册要求先做什么？”答案需要C1、C2、C3共同支持。

## 一、摘要树：向上概括，向下找依据

```text
                    ROOT：全体档案摘要
                    /              \
          S1：青禾蜂场摘要       S2：白石蜂场摘要
           /  /  \  \             /  /  \  \
          C1 C2  C3 C4           C5 C6  C7 C8
```

程序先让模型分别读C1～C4、C5～C8，写出S1、S2，再根据这两份摘要写ROOT。每个摘要节点保存children和source_ids，原始叶子没有被删除。

模型生成的S1包含：蜂群A发现蜂螨；手册M先监测蜂螨数量；冬季保温与饲料检查。查询概览时，读取S1便能得到这些管理主题；查询细节时，可以按children展开C1～C4。

这展示的是两种阅读粒度，而不是证明本例必须用树：原始资料很短，直接读取四段也能回答。生产规模下，摘要层的作用是减少先读的细节，并保留回查入口。

实际也出现了压缩风险：原文“青禾蜂场管理蜂群A”，摘要写成了“青禾蜂场位于河谷镇，蜂群A管理”，关系变得含糊；“蜂螨防治参考手册M”这一明确连接也没有完整保留。摘要来源包含C1～C4，不代表这四段的每条事实都已保留。精确关系仍应核对叶子原文。

## 二、关系图：让跨段关系成为可遍历的边

三元组形如：`主体 --关系--> 客体`。每条边还保存source_id和原文，使路径可回查。

第一次抽取里，模型把C2的一条关系写成：

```text
蜂螨防治参考手册 --参考--> M
```

而C3中的实体叫`手册M`。于是“蜂螨”“蜂螨防治参考手册”“M”“手册M”成了不同节点。从青禾蜂场出发只能走到：

```text
青禾蜂场 → 蜂群A → 蜂螨    （到不了手册M）
```

这不是资料缺失：C3就在输入中；而是实体切分和命名让图断开了。同名对象连接不上，遍历算法也无法恢复关系。

### 一个受控对照：限制实体名称

保留首轮输出，只对C2重新调用模型，规定端点只能取`蜂群A、蜂螨、手册M`。这是人工给定实体名单，不能冒充自动实体链接。

模型这次实际输出：

```text
[C2] 蜂群A --发现--> 蜂螨
[C2] 蜂螨 --防治参考手册--> 手册M
```

从指定起点“青禾蜂场”做最多4跳的有向遍历，得到：

```text
青禾蜂场 ─管理[C1]→ 蜂群A
                        └─发现[C2]→ 蜂螨
                                     └─防治参考手册[C2]→ 手册M
                                                           └─要求[C3]→ 监测蜂螨数量
```

遍历前后的实际差异：

| 结果 | 原始命名 | 限定命名后 |
|---|---|---|
| 到达手册M | 否 | 是 |
| 路径取得C3证据 | 否 | 是 |
| 模型回答 | 编造“手册[C1]、先检查蜂群状态” | 回答“手册M，先监测蜂螨数量” |

缺证据时的编造没有改成正确答案。限定命名后的回答内容与原文一致，但仍没按要求标注来源引用，不能说所有回答要求均已满足。

## 三、建图不等于获得真理

原始关系中还出现了“饲料 --缺少--> 饲料”等问题边。即使两端文字都能在原文找到，关系也可能不正确。因此本实验的端点子串检查只能发现部分格式或落地问题，不能代替语义审查。

第一轮还有一个读取程序问题：模型返回JSON数组，程序只接受带edges字段的对象，导致最初图为空。后续兼容两种容器后，复用原始关系，没有人工编造边。格式问题、实体命名问题和关系正确性是三个不同层次。

## 如何选择结构？

| 问题类型 | 更值得先尝试的组织方式 | 仍需检查 |
|---|---|---|
| “这份手册总体讲什么？” | 摘要层级 | 摘要是否漏项或改写关系 |
| “这个细节的原文在哪里？” | 摘要定位后展开叶子，或直接混合检索 | 证据是否完整、版本是否适用 |
| “A关联谁，经过哪些关系到B？” | 实体关系与多跳遍历 | 命名、方向、边真实性、来源 |

两种结构可以组合：先看概要，沿关系找到有关对象，再回原文核对。普通检索已经能完成的任务，不必增加结构化索引成本。

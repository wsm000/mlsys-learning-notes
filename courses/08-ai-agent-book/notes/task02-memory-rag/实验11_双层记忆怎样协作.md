# 3-11：卡片提示要查什么，原文核验能说什么

## 本实验想实现什么机制？

像蜂场总览卡写着“蜂群A有病史”，它提醒助手回查巡蜂记录；原始记录才说明什么时候发现、采取过什么措施、目前是否仍适用。

双层记忆把两种职责组合起来：

```text
结构化记忆卡片：人物／事件／状态／时间／关键字段
                         ↓ 提示核验方向
带背景前缀的原始会话索引 → 定向检索 → 原文证据
                         ↓
             核对对象、动作、时间、适用条件
                         ↓
                   有依据的主动提醒
```

卡片不是新的权威来源，原文库也不会因为存在就自动被查询。连接二者的“触发查询、核验与状态维护”才是关键机制。

## 实际输入与范围

使用教材原三层套件的一个layer3旅行协调用例，3次虚构历史会话、42个4轮窗口：护照咨询、航班预订、信用卡准备。原问题只是问“我在敲定一月去东京的行程，出发前还需要处理什么？”并未逐项指定要查护照、保险或休息室。

本轮比较：普通RAG、上下文RAG、原最终卡片＋上下文RAG、受控保留卡片＋上下文RAG。前缀由本地Qwen3-0.6B读完整来源会话与目标块实际生成；索引使用真实BGE、BM25与RRF。卡片复用3-1中DeepSeek-V4-Flash的真实输出和原始调用出处，没有按本轮问题手写正确事实。

这是等价机制实验，不是60例全量双层验收。卡片触发查询采用固定的类别／字段名规则，不冒充模型自主规划。双层分支获得更多卡片与证据，不能把结果差异单独归因于一种架构。

## 一、先发现卡片维护本身的问题

此前3-1真实快照的变化为：

```text
第1次：护照卡
第2次：护照卡＋航班卡
第3次：只剩信用卡卡
```

原最终快照丢掉了前两类信息。因此增加受控对照：从既有逐会话快照中按card_key保留时间戳最新版本，得到护照、航班、信用卡3张卡。原始快照未改写，受控层另外保存。

这不是完整生产记忆维护方案：没有实现删除、撤销或墓碑语义，不能把“全部累积”当作通用正确做法。此处只用于展示：概览层丢失一个主题，会减少后续核验入口。

## 二、卡片怎样触发回查？

程序从卡片类别、人物和字段名构造短查询，实际发出的查询包括：

```text
passport renewal Jessica Martinez passport expiration date
flight booking Jessica Martinez confirmation number return date payment card expiration
credit card Jessica Martinez travel insurance business trip coverage ...
```

只有信用卡卡片时，额外检索主要进入信用卡会话。保留3张卡后，又找到了护照到期记录等证据；原始会话仍作为事实核验来源，而非把卡片内容自动视为最终结论。

## 三、四条路径实际表现

| 路径 | 实际观察 |
|---|---|
| 普通RAG | 已找到护照和航班片段，但回答把2月18日写成2月15日，并混淆办理时间 |
| 上下文RAG | 命中证件照片等背景，回答未抓住准确到期日 |
| 最终1张卡＋RAG | 补出信用卡、休息室主题，仍没清楚解释护照到期与行程的关系 |
| 保留3张卡＋RAG | 取回更多护照、航班、付款条件证据，但生成仍出现动作混淆、来源错配 |

所以本轮不能宣称“双层记忆回答通过”。普通分支原本就已提到护照，也不能说只有卡片才发现这个主题。观察到的是卡片能增加定向检索入口，并不自动保证最终提醒正确。

## 四、追到原文，才看清错误发生在哪

双层回答出现：“passport renewal deadline is 72 hours before departure”，并引用H1。

但卡片字段叫`passport_update_deadline`，对应原始H19写的是：

```text
USER: I was thinking about renewing anyway. Can I update the passport number later?
ASSISTANT: Yes, you can update it up to 72 hours before departure.
```

这是向航空公司**更新护照号码**的历史说法，不是办理**护照续办**的截止时间。H1也不能支持模型写出的72小时结论。

这说明验证不能只检查“72小时这个数字在哪里出现过”，还要检查它修饰哪个动作。记忆字段关联错位，即便数字来自真实来源，结论仍然不受支持。

## 五、做了一个字段级核验回放

从保留卡片的字段名与值构造更精确的BM25查询，直接查询保存的原始块：

| 卡片字段 | 回查到的原文 | 能核对什么 |
|---|---|---|
| passport_expiration_date | H17、H1 | 记录中的到期日是2025-02-18 |
| return_date | H17、H15 | H15记载1月22日返程；年份仍需结合卡片和会话背景 |
| passport_update_deadline | H19、H18 | 72小时对应向航司更新护照号码 |
| business_trip_coverage | H32、H34 | H32的保障描述带“以指定卡付款”的条件；并非整趟旅行自动受保 |

这是人工规定的字段查询策略，在本地重放真实检索分数，不是模型自主补救，也没有把模型原始错误回答改成正确答案。部分返回片段不相关，仍需逐条读证据。

程序按卡片记载的返程日2025-01-22和到期日2025-02-18计算，间隔为27天。这是一个可复核的日历事实，不能单独推出任何实际入境或登机结论。

原基准的历史对话与评分标准在护照有效期、处理时长方面存在不一致。本实验不采用评分标准中的普遍化断言作为现实规则，也没有查询当前政策；所有这里的证件、银行与保障描述仅作为虚构历史证据分析。

## 这个机制的边界

- 卡片提供“值得核验的线索”，不应无条件覆盖原文。
- RAG提供具体来源，但还要检查条件与时间是否适用。
- 程序可以完成日期计算、字段匹配和来源定位；这些检查不等于完整语义判断。
- 生成模型仍可能把“决定办理”说成“已经办理”，或把一个动作的期限套到另一个动作上。

本轮的主线是**概览触发 → 原文回查 → 条件核验 → 提醒**，而不是把两个存储系统接上后就宣称有了可靠主动服务。

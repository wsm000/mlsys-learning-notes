## 0. 这次多 Agent 是怎么被"用"起来的：四个 Agent 的真实协作

这次任务本身就是一次第 10 章的现场演示，值得先记下来。

**Manager（Lead）** 先完成不可外包的部分：读 PDF 第 10 章正文、确认上游课程仓库结构（注意：主分支 `chapter10/` 下是 `multi-role-transfer`、`book-translation`、`parallel-web-research`、`voice-werewolf` 等按"实验编号"组织的项目，**没有**一个通用的 Planner→Researcher→Executor→Reviewer 教程目录），然后探测运行环境（网络可达性、本地 8789 端口的 Responses API 代理、Python 版本、缺少的包）。这一步是 Manager 的 `Plan`，也是 Plan-and-Act 那篇论文说的"弱规划者是全系统瓶颈"的关键环节。

**拆解按"证据独立性"而不是按"话题"来切**：四个工作包分别产出互不重叠的证据目录，写作用 `write_scopes` 划清边界。三名子 Agent 的角色差异不只是提示词不同——它们的输出格式（源码快照 / 指标 JSON / 可跑实验）、验收方式（行号可核对 / 数字可重算 / 断言可重跑）、失败处理完全不同。

**信息传递走的是文件系统而不是对话**：每个工作包的回传约定是"产物路径 + 可重算的 summary"，而不是把整段思考塞回 Manager 的上下文。这正是书里 10.4.1「Agent 眼中的虚拟文件系统」和"子 Agent 返回结构化摘要而非全量轨迹"的工程形态。

**Lead 自己做的是什么**：不是转述子 Agent 的结论，而是**写不依赖它们就能成立的那部分**，并负责最后的交叉核对（见 M2 §6 的验收表）。这对应书里 10.5.6「理解债与认知投降」——把理解一起外包出去，是这类系统里最难被检测到的失败。

## 1. Single-Agent 与 Multi-Agent 到底差在哪

### 1.1 不是"能力变多"，而是"信息变新"

书里给出的第一判据只有一句：**协作过程是否引入了单个 Agent 在生成时无法获得的新信息？**（10.2，表 10-1）

| 协作模式 | 是否引入新信息 | 书里给出的效果 |
|---|---|---|
| 同一模型自我审查（重读自己的输出） | 否 | 通常无效，甚至有害 |
| 不同 Agent 辩论同一段文本 | 否 | 等计算量下与单 Agent 持平 |
| 审核者用**测试执行结果**审查代码 | 是（执行反馈） | 显著提升 |
| 审核者看**渲染截图**审查前端/PPT | 是（视觉反馈） | 显著提升 |
| 审核者用**外部工具**验证事实 | 是（工具反馈） | 显著提升 |

这条判据解释了一个长期争论：学术研究常报告"多 Agent 不比单 Agent 强"，工程实践却常报告"明显更强"。差别在于两边讨论的不是同一种多 Agent——前者多是"多个 Agent 看同一段上下文互相讨论"，后者几乎总带着一个外部反馈环（代码执行、渲染截图、工具验证）。

**我的理解**：单 Agent 与多 Agent 的分界，不在于"有几个进程/几个提示词"，而在于**信息流是否存在一条单 Agent 走不通的通道**。如果拆出来的两个 Agent 之间只传递"想法"，那本质上还是同一个模型的同一条思维链，只是把上下文切成了两半，还额外付了转述损耗。

> 证据对应：[task05-ch10-shared-context.md](task05-ch10-shared-context.md) 里的审查者两臂对照（只看答案 vs 看独立执行证据），就是给表 10-1 这条判据做的本地复现。

### 1.2 与单 Agent 的量化差别在哪三处

| 维度 | 单 Agent | 多 Agent | 代价 |
|---|---|---|---|
| 上下文 | 线性增长，受窗口限制 | 可隔离，各自精简 | 信息同步成本、接口设计成本 |
| 能力边界 | 一个模型的全才程度 | 可用不同模型/工具/权限 | 编排复杂度、单点瓶颈（Manager） |
| 错误模式 | 思维链内自我强化 | 可能交叉验证，也可能**级联放大** | 拜占庭式故障，需要独立的验证方 |

第 7 章说过 Agent 的故障天生是**拜占庭式**的：它很少径直停摆，而是继续给出看似可信的错误结论。多 Agent 的价值本质上是用"独立视角"去对冲拜占庭故障；多 Agent 的风险也来自同一处——如果各 Agent 同源同构，独立视角就是假的（10.5.3 同质趋同：Anthropic 实验里 30 个同时上线的 Agent 有 18 个创建了同名 Git 分支）。

### 1.3 成本是第一性约束

多 Agent 的并行探索与反复迭代都要烧 token。书里的判据是：**收益必须足够大到覆盖数倍乃至一个数量级的额外开销**，否则一个调校得当的单 Agent 更划算。本目录的实测里，Manager 模式的上下文缩小了，但总 token 未必更少——见 M2。

## 2. 角色设计：角色是接口，不是人设

### 2.1 一个角色的五件套

从书里 4.7「协作工具」与 10.4 的表述中提炼，一个可用的角色定义至少要写清五件事：

| 要素 | 要回答的问题 | 漏掉之后的典型故障 |
|---|---|---|
| 职责边界 | 我负责什么，什么必须转交/上报 | 10.5.4 互相扯皮 |
| 输入契约 | 我从哪里拿什么，格式是什么 | 下游重复劳动或误解 |
| 输出契约 | 我交付什么，验收标准是什么 | "声明完成"被当成"完成" |
| 工具与权限 | 我能看到哪些工具、能动哪些资源 | 越权写共享空间、语义冲突 |
| 终止条件 | 什么条件下我可以停 | 10.5.5 循环失控 / 过早终止 |

书里 10.4.3.1 的三种"过早终止"特别值得记住——偷懒式假完成、过早放弃、假成功——它们的共同根源是：**在验证之前，"完成"只是模型的一句宣称，不是证明**。

### 2.2 让角色真正"不同"

多个实例 ≠ 多种思路。要拿到真正的多样性，必须主动区分**模型、上下文、工具、可见证据、职责**中的至少一项，并让各 Agent **先独立判断、再汇总**。否则就是 10.5.3 的同质趋同：同一模型、相似上下文产出的多份意见，不能当作相互独立的证据。

用这次的真实例子说明：三名子 Agent 用的是同一个底层模型，它们的独立性来自**制品类型和验收方式**（源码行号核对 / 指标可重算 / 测试可重跑），而不是"人设不同"。这已经是能拿到的最小代价多样性；如果三份笔记都由同一个 Agent 写，它们互相"印证"是没有信息量的。

### 2.3 角色规程的载体：替换 system prompt，还是加载 Skill？

这是书里 10.3 指出"常被忽略但会直接改变架构"的设计选择：

| 选择 | 工具可见性 | 上下文 / KV Cache 影响 | 约束能力 |
|---|---|---|---|
| `transfer_to_agent`（换 system prompt + 换工具集） | 只暴露当前角色工具 | 每次切换都改变请求前缀，**前缀缓存通常无法复用** | 强：越界工具在 schema 层不可见 |
| Skill（固定 system prompt + 完整工具集，按需把 SKILL.md 追加到轨迹） | 通常暴露工具全集 | 静态前缀不变，Skill 内容成为**末尾轨迹**，前缀可继续复用 | 弱：Skill 只是行为指令，硬权限仍要靠 Harness 门 |

经验规则（书里原话）：
- 角色差异主要来自**知识、流程、写作风格** → 优先 Skill；
- 角色差异涉及**权限、工具隔离、合规边界** → 用独立 Agent / `transfer_to_agent`，并在 Harness 层用代码限制工具调用。

这条规则的工程含义是：**Skill 是"软规程"，Agent 是"硬边界"**。把安全边界写进 Skill，等于把门禁交给被管的人自己执行。

> 证据对应：本目录把"角色切换 vs Skill 加载"做成了对照实验，见 [task05-ch10-shared-context.md](task05-ch10-shared-context.md)。

## 3. 任务拆解与分工

### 3.1 两个正交的设计维度

书里 10.1 给了两个决定架构的维度：

**维度一：上下文是否共享**

| | 共享上下文（继承式） | 不共享上下文（隔离式） |
|---|---|---|
| 传递方式 | 直接继承完整轨迹 | 必须显式通信：工具调用参数 / 共享文件系统 / 消息总线 |
| 优势 | 信息不丢失，可回顾任何阶段细节 | 模块化、可扩展、可并行、权限可隔离、故障不传染 |
| 风险 | 上下文快速膨胀、**角色惯性**（继承"需求分析师"上下文的"代码审查员"仍在用需求视角思考） | 信息同步复杂、调试要拼多个 Agent 的日志 |

**维度二：协作拓扑**

- **对等协作**：少量 Agent 按固定拓扑迭代（提议者-审核者、辩论、头脑风暴、专家小组）；
- **管理者编排**：中心 Manager 分解与调度，子 Agent 被建模为可调用的工具；
- **去中心化**：没有运行时中心，控制权在 Agent 之间移交（handoff），或靠消息池+订阅解耦。

这两个维度正交，所以会出现"共享上下文 + 管理者""不共享上下文 + 对等"这些组合。判断一个产品属于哪类，要看**上下文怎么流**和**控制权怎么流**，而不是看它叫不叫 "Swarm"。

### 3.2 Agent 间通信 = 进程间通信（IPC）

书里把多 Agent 系统与操作系统的对应关系列成表（表 10-2），这是全章最省力的心智模型：

| 操作系统 | 多 Agent 系统 |
|---|---|
| 程序（可执行文件） | 静态前缀（system prompt + 工具定义） |
| 进程的内存 | 轨迹 |
| CPU | LLM |
| 内核 | Agent 运行时 / Harness |
| 系统调用 | 工具调用 |
| fork | `spawn_subagent` |
| kill | `cancel_subagent` |
| ps | `list_agents` |
| 退出码与 wait() | 子 Agent 返回的结构化摘要 |
| 共享内存 / 消息传递 | 共享文件系统 / 消息总线 |

通信机制也落在 IPC 的两大范式里：

1. **工具调用的参数**——把下游 Agent 封装成工具，结构化数据随调用同步传递（类型确定）；
2. **共享文件系统**——通过共享目录交换中间产物，适合产物大或需持久化（Agent 世界的"共享内存"）；
3. **消息总线**——Agent 不直接互调，而是发布到总线，由总线按订阅转发（异步、解耦，点对点连接数不会随 Agent 数平方增长）。

经验法则借 Go 那句："不要通过共享内存来通信，而要通过通信来共享内存。"

### 3.3 文件系统是数据平面，消息与控制是控制平面

书里把 Agent 看到的文件系统拆成四类区域（表 10-3），这是设计共享工作区时最实用的一张检查表：

| 区域 | 可见性 | 生命周期 | 读写 | 并发控制 |
|---|---|---|---|---|
| Agent 专属工作区 `/scratch/<id>` | 仅该 Agent | 随实例销毁 | 读写 | 不需要（私有） |
| 多 Agent 共享空间 `/workspace/shared` | 所有协作 Agent + 用户 | 随任务，需持久化 | 读写 | **需要**：乐观锁 / worktree |
| 外部挂载资源 `/mnt/gdrive` | 视外部授权 | 由外部源决定 | 多为只读 | 由外部源负责 |
| 系统内置资源 `/skills` | 所有 Agent | 跨会话稳定 | 只读 | 不需要 |

**本次实践的对应**：`write_scopes`（每个工作包只写自己的目录）相当于把"专属工作区"落到任务板上；`evidence/task5/` 与 `notes/` 是共享空间，只读共享的课程源码快照 `_upstream/` 是系统内置资源。相当一部分并发冲突与信息泄露，正来自把本应隔离的区域混置。

控制平面四件事（书里 10.4.2），每一件都比看起来重要：

1. **消息传递**：统一信封 `{sender, target, type, payload}`，类型如 `task_assigned/status_update/result/terminate`。统一信封让链路可追溯——这是多 Agent 调试的关键。
2. **状态查询**：不要用拉取式 `get_subagent_status` 硬查；用消息问进度，或用**进度文件**（`progress.md`）。轨迹持久化（JSONL 逐行追加）能"直接读另一个进程的内存"，但几万 token 的轨迹不适合当主通道。进度文件的修改时间还能做**卡住检测**。
3. **执行终止**：优雅终止（`terminate` → 安全点清理 → `ack`）优先，强制终止兜底；终止沿创建关系**向下级联**（Go 的 `context` 语义），从根上杜绝孤儿 Agent。
4. **资源与调度**：稀缺资源是 token 与并发额度。启动子 Agent 时设步数/token 预算、并发上限、抢占；困难任务给强模型，机械任务给低成本模型。

### 3.4 预算感知：为什么"多给步骤"不等于"更好"

书里引用的 Budget-Aware Tool-Use 研究给了一个反直觉结论：把步骤从 30 加到 300 并不自动变好——标准 Agent 缺乏**预算意识**，会在浅层搜索后"饱和"。要让步数变现，需要显式预算感知：前期广泛探索，后期聚焦最有希望的方向。

对 Manager 的直接含义：不要平均分配预算，而应**按子任务复杂度动态分配**，并引导子 Agent"先规划、再实现、再测试、再改进"。

> 证据对应：[task05-ch10-parallel-orchestration.md](task05-ch10-parallel-orchestration.md) 里对比了同一批站点的串行与并行墙钟时间——并行省的是**墙钟**，不是 **token**，两个预算要分开记。

## 4. 典型工作流

### 4.1 Planner → Researcher → Executor → Reviewer（题面那条链）

这是最常见的顺序编排，本质是**管理者模式的顺序形态**，也可以落在 MetaGPT 那样的 SOP 流水线上：

```text
Planner    产出：任务清单 + 每步验收标准 + 预算
Researcher 产出：带出处的证据（每条结论能指回原始来源）
Executor   产出：可运行的产物（文件 / 代码 / 数据）
Reviewer   产出：基于独立证据的裁决（通过 / 退回 + 可定位的修复条件）
```

三个容易做错的地方：

1. **Planner 是瓶颈**。Plan-and-Act 的实证结论：弱规划者是全系统最大的瓶颈；规划一旦分解错，后面所有 Executor 都在错误前提上工作。所以最强模型和最好的提示词应该给 Planner，而不是平均分配。
2. **Reviewer 必须拿独立证据**。审核者不能修改测试、证据采集器或发布门槛，否则"独立验证"退化成自我批准。提议者-审核者循环的最小不变量是：审核者读取独立证据，退回时必须给出**可定位**的修复条件。
3. **Resolver 要区分"第一个声称成功"和"第一个已验证成功"**。书里给了并行版伪代码：`settle_once` 必须在锁/事务保护下幂等，否则两个几乎同时到达的成功事件会触发两次汇总。

```text
candidate = proposer(task, constraints)
evidence  = execute_or_render(candidate)         # 测试、状态、截图、事实
review    = independent_reviewer(candidate, evidence)
while review.veto and budget_remaining:
    candidate = proposer.repair(candidate, review.findings)
    evidence  = execute_or_render(candidate)
    review    = independent_reviewer(candidate, evidence)
publish(candidate, evidence, review) if review.pass else escalate_or_reject(review)
```

> 证据对应：本目录的并行检索实验就实现了 `asyncio.Lock` 下的单次结算、恰好一次 terminate 广播与未胜出 worker 的 ack，见 [task05-ch10-parallel-orchestration.md](task05-ch10-parallel-orchestration.md)。

### 4.2 对等协作的四种变体

| 变体 | 适用 | 注意 |
|---|---|---|
| 提议者-审核者 | 代码、PPT、文档质量提升 | 必须有外部证据；否则等同自我审查 |
| 辩论 | 需要正反两面充分论证 | 等计算量下常与单 Agent 持平（数据处理不等式：同一批信息串行转述只会丢信息） |
| 头脑风暴 | 探索解空间 | 多样性必须来自差异化提示词/模型 |
| 专家小组 | 跨学科评估 | 各视角是互补而非对抗 |

书里还有一个争议结论值得记：**辩论模式的收益往往来自"花了更多算力"**，而不是"辩论"本身。真正站得住的是两类做法——对同一问题多次独立采样再聚合（自一致性、多数投票），以及利用"生成难、验证易"的不对称做生成-验证分工。

### 4.3 管理者模式：顺序与并行

- **顺序协调**：Manager 依次调用 `call_agent_A → B → C`，控制流线性，适合子任务有清晰先后依赖；
- **并行协调**：多个 Agent 同时工作，Manager 需要消息总线做实时监控与全局决策。核心难点是**级联终止**（一个成功，全员停止）与**竞态**（近乎同时的两次命中只结算一次）；
- **工作流即代码**：管理者先生成一段确定性工作流（`agent()`/`parallel()`/`pipeline()` 这类原语），再交给运行时执行。相比"每派发一个子任务都要模型决策一次"，这样做上下文不随调用次数膨胀。

工程上"调用一个 Agent"和"调用一个工具"应尽量同构——Manager 只需扩展工具表就能接入新能力，天然支持异构模型与异构环境。

### 4.4 去中心化：三层解剖

| 系统 | 控制流 | 通信 | 它到底证明了什么 |
|---|---|---|---|
| MetaGPT | **固定 SOP 流水线**（伪去中心化） | 共享消息池 + 按角色订阅 | 真正的贡献是**解耦**：换掉一个角色的模型，只要输出格式不变，下游零修改 |
| AutoGen GroupChat | 中心化的发言者选择器 | 共享对话记录 | "共享对话 + 中心调度"的混合形态 |
| OpenAI Swarm | 真对等，handoff 移交 | 移交包（task_id/goal/constraints/accepted_facts/artifact_refs/remaining_budget/visited_agents） | 对等移交的风险是**成环**，必须有 visited 集合与预算上限 |

这里要提醒自己：2025 年以来 "Agent Swarm" 被各厂商用得极乱，有些是真 handoff 网络，有些其实是**规模化的管理者模式**（主 Agent 动态创建上百个子 Agent）。看结构，不看名词。

### 4.5 跨组织：A2A

单团队内部用参数/文件/消息总线就够了；跨信任边界时才需要 A2A 这样的公开协议。三要素：

- **Agent Card**：描述能力的元数据（能做什么、支持什么模态、如何认证）——解决能力发现；
- **任务生命周期**：Task 状态机（已提交/进行中/需要输入/已完成/失败），原生支持长任务与流式进度；
- **不透明协作**：只交换任务与产物，不暴露提示词、思考过程与工具实现——与"不共享上下文"原则一致。

定位对照：**MCP 解决 Agent↔工具，A2A 解决 Agent↔Agent**。

### 4.6 Loop 工程：让"完成"变成可验证的事

过早终止（假完成、过早放弃、假成功）的根源是缺一个**验证器**。Loop 工程把循环从提示词里抽出来，放进控制面：目标与边界、门禁与待办、证据与配额、移交。两个框架的差异值得注意：

- **LoopX**：与 Agent 运行时解耦的持久控制面；"模型可以提出完成，但不能批准自己的完成"；
- **LongHorizon-Harness**：Manage–Execute–Audit 循环，把长程执行重述为**任务状态管理**——上下文可以刷新，但下一轮从最近一次核实的状态继续。论文报告 WeaveBench PassRate 51.8%→80.7%，代价是 2.3× 总 token。

**收益与代价必须一起记**：这一类改进几乎总在"用显著更多 token 换质量"。

## 5. 什么时候该用多 Agent，什么时候单 Agent 就够

把全章的判据收敛成一张检查表，按顺序问：

| # | 问题 | 如果答"是" | 如果答"否" |
|---|---|---|---|
| 1 | 协作是否引入了单个 Agent 生成时拿不到的新信息（执行结果、渲染截图、外部工具验证、不同数据源）？ | 继续 | **单 Agent 就够**，多 Agent 只会更贵 |
| 2 | 任务能否被切成**并行**互不依赖的部分？ | 并行编排收益大（省墙钟） | 顺序编排即可，别强上并行 |
| 3 | 是否存在**上下文隔离**的真实需求（单章翻译、单站点检索、单模块开发）？ | 隔离式协作 | 共享上下文更省事 |
| 4 | 是否存在**权限/工具/合规边界**需要硬隔离？ | 独立 Agent + Harness 门禁 | 用 Skill 做软规程 |
| 5 | 质量提升能否覆盖数倍以上的 token 与延迟成本？ | 可采用 | 用更强的单 Agent + 更好的验证器 |

反过来，以下情况**不该**上多 Agent：

- 只是想让模型"再想想"——自我审查在无外部反馈时通常无效甚至有害；
- 想在等计算量下靠"辩论"提升准确率——多数实验显示持平；
- 任务本身串行且短——编排开销会超过收益；
- 团队还没有可靠的验证器——"循环的瓶颈在验证器，而不在模型"。

**我的一句话总结**：多 Agent 不是"更大的模型"，而是**一套用额外开销购买信息多样性与并行度的组织设计**；买不到新信息的多 Agent，只是在为一个更贵的单 Agent 付账。

## 6. 失败模式速查（10.5）

| 失败模式 | 机制 | 对策 | 本目录的对应 |
|---|---|---|---|
| 共享文件系统并发冲突（文件级 / 语义级） | 后写覆盖先写；跨文件逻辑矛盾 | 乐观锁（版本号/CAS）；worktree 隔离；语义校验 | `write_scopes` 隔离 |
| 错误的级联放大 | 每转述一次都是有损重编码 | 交叉验证：只看原始证据与结论是否一致，不看前序思考过程 | 审核者拿独立证据那组 |
| 同质趋同 | 共同模型/脚手架导致共因失效 | 差异化模型/上下文/数据源；命名空间、配额、限速 | 角色靠制品类型区分 |
| 互相扯皮 | 目标互斥、责任不清 | 预设目标优先级、资源所有权、权限边界；无法按规则解决时暂停交人裁决 | 明确的 write_scopes |
| 循环失控 | 自主性过强、无预算 | 独立 API key、token 预算、并发上限 | 每站点超时 + 预算 |
| 理解债 / 认知投降 | 人不再理解交付件 | 人必须能独立复算关键结论 | Lead 亲自写概念部分并交叉核对 |

## 7. 本章留下的思考题（我选了 3 道写想法）

**题 1：共享上下文中的"角色惯性"怎么检测和消除？**
检测可以靠对照：同一任务在"继承完整轨迹"与"只继承结构化移交包"两种输入下各跑一遍，比较审查意见的**分布**（例如代码审查里"功能正确性 vs 需求完整性"话题的比例是否显著偏移）。消除的方法不是删历史，而是**改变证据的呈现顺序**：让审查者先看独立证据（diff、测试结果），再看历史；或者让审查者在独立上下文中开一轮，再由调度层做合并。

**题 2：如何确保 Manager 的分解质量？**
分解质量的验收标准应该是**可执行**的：每个子任务必须带输入契约、输出契约和验收条件，且验收条件能被独立复核。可以把"分解"本身当成提议者-审核者的一轮——Planner 出计划，一个独立 Agent 只读原始需求与计划、不看 Planner 的理由，检查"是否漏项、是否可验收"。这就是让验证器成为瓶颈，而不是让 Planner 自我感觉良好。

**题 4：高效的级联终止该怎么做？**
书里实验 10-4 的时序给出了骨架：找到目标 → `target_found` → Manager 在锁下**只结算一次** → 广播 `terminate`（恰好一次）→ 未胜出 worker 在**安全点**响应、清理、回 `ack` → Manager 等到全部 ack 或超时后汇总。两个细节最容易漏：一是晚到的命中要记成 duplicate 而不是触发第二次汇总；二是"发了 terminate"不等于"停下来了"，必须用 ack 和资源关闭计数去核对。

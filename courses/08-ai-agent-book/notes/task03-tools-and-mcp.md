# 给 Agent 接上手脚：Tools、MCP，以及一次实验到底证明了什么

一个语言模型可以写出启动实验的命令，也可以解释日志中的异常。但如果没有外部接口，它生成的命令只存在于文本里，实验不会启动，文件不会改变，服务器也不会收到请求。

Tools 把这个缺口接起来。模型选择工具并生成参数，运行时检查请求、调用具体实现，再把结果放回模型上下文。模型据此决定下一步，形成一个与外部状态持续交互的循环：

```text
观察 → 判断 → 调用工具 → 外部状态变化 → 获取证据 → 再次判断
```

一个 Agent 是否可靠，既取决于它选择了什么动作，也取决于它能否准确知道动作之后发生了什么。

围绕《深入理解 AI Agent》第四章，在远端 Linux 环境运行了 `execution-tools` 的部分机制实验，并做了 MCP 通信、业务结果校验和审批超时实验。本文以中文版 PDF 为章节依据：书内第 103 页开始讨论工具分类，第 119 页给出实验 4-4 的要求。

## 工具的五类划分，描述五种交互关系

把 Agent 放在一张图中央，可以沿着信息与控制流向理解五类工具。

| 类别 | 核心作用 | 典型动作 |
|---|---|---|
| 感知 Perception | 获取外部信息 | 搜索文档、读取日志、查看截图 |
| 执行 Execution | 改变外部状态 | 写文件、启动实验、发送邮件 |
| 协作 Collaboration | 把任务交给其他执行主体 | 创建子 Agent、委派任务、接收结果 |
| 事件触发 Event Trigger | 在条件满足时推动 Agent 开始或恢复运行 | 定时唤醒、订阅新邮件、监听任务结束 |
| 用户沟通 User Communication | 向用户传递信息或获取决定 | 汇报进度、提出问题、请求批准 |

这套划分关心一次交互承担的作用。代码是否运行、是否经过网络，都不足以决定类别。`search_logs(query)` 会运行搜索程序，但它承担的是感知；`start_experiment(config)` 创建实验进程，承担的是执行。

同一个流程通常包含多种作用。凌晨到点，定时器唤醒 Agent，这是事件触发。Agent 读取昨天的实验日志，这是感知。它委托子 Agent 分析失败原因，这是协作。分析结束后询问用户是否重跑，这是用户沟通。获准后启动实验，才进入执行。

事件触发有两个时间点。注册定时任务时，Agent 主动声明自己关心的条件；条件满足后，外部运行时负责唤醒它。持续读取时钟并判断是否到点，也能实现类似行为，但那是一种轮询式感知。两种实现的结果可能相同，运行机制和资源开销不同。

这五类没有构成严格的物理边界。一个服务器可以同时提供读文件、改文件和委派任务的接口。分类的价值在于提醒设计者关注不同的问题：读取要控制信息量，写入要管理副作用，委派要明确责任与验收。

## 感知工具决定模型能看到什么

模型可用的上下文有限。读取一份长日志时，把全部内容直接返回，看起来最忠实，却可能消耗大量上下文，并让关键错误埋在重复输出中。

因此，感知工具需要提供可调节的观察粒度。搜索可以先返回标题、位置和摘要，让 Agent 选择需要深入的条目；读取文件可以支持 `offset` 和 `limit`；结果过多时可以使用分页或游标。每次返回都应让 Agent 知道自己看到了什么范围，以及如何获取剩余内容。

截断必须显式可见。假设日志有 1000 行，工具只展示前后各 50 行，却没有说明省略了中间部分。Agent 很容易把局部观察当成完整观察，随后形成一个自己无法察觉的错误判断。

我们的长输出实验使用课程原始实现生成 1000 行文本。工具返回的可见输出为 102 行，包含头尾内容以及截断与读取提示，完整的 1000 行另存文件。随后又将原始输出复制到持久学习目录，避免实验记录只依赖临时文件。

这个结果证明了两件事：返回上下文的内容可以减少，原始证据仍然能够保留。它没有证明压缩后的内容足以支持所有判断。

考虑一个更难的例子：第 500 行出现错误，最后一行写着 `Done`。单纯保留头尾会遗漏决定性线索。更好的设计是在截断前提取诊断位置，再同时返回退出码、错误候选、展示范围和完整日志引用。这是基于实验提出的改进，本轮没有实现该诊断提取器。

错误候选与失败结论仍要分开。日志中的 `ERROR` 可能来自已恢复的重试，也可能出现在测试样例中。检测器可以报告匹配位置，业务验证器则需要判断这些事件是否影响任务目标。

这产生了两种预算：上下文预算决定本轮展示多少信息，证据保留策略决定之后还能追查什么。摘要负责降低阅读成本，原始记录负责支持复核。

## 执行工具把语言变成副作用

读取日志出错，通常意味着理解偏差；执行动作出错，则可能留下持久影响。重复启动实验会浪费资源，重复追加文件会污染数据，重复发送邮件会产生用户可见的事故。

执行工具需要在几个独立层面约束动作。输入验证检查参数是否合法，例如路径是否越出工作目录、枚举值是否有效、配置文件是否满足格式要求。权限控制检查当前身份是否有权操作目标。执行环境限制代码能够访问的文件、网络和资源。结果验证再检查实际产物是否符合任务要求。

这些层次不能互相替代。路径检查通过，不代表调用者有权访问该文件；语法检查通过，不代表计算正确；在 Python 虚拟环境里执行，也不意味着代码处于安全沙盒。虚拟环境主要隔离依赖，代码仍可能拥有当前用户的文件和网络权限。

代码执行返回了明确的环境信息：

```json
{
  "kind": "local-process",
  "degraded": true
}
```

对不可逆操作，还需要处理审批和超时。审批服务超时意味着没有取得有效结论。此时可以保持动作未执行，同时返回 `approval: "unknown"`。把它记为明确拒绝，会丢失恢复所需的信息；默认放行，则把审批故障转化为授权。

执行阶段的超时则更棘手。请求可能已经到达服务端，操作也可能完成，只是响应没有返回。此时重新发送同一请求，可能产生第二次副作用。

幂等机制通常需要客户端在提交前生成请求标识，由服务端持久化去重。同一标识携带相同请求重试，应关联到同一次操作；同一标识携带不同内容，则需要明确处理冲突。服务端生成的 `run_id` 适合追踪任务，但如果第一次响应丢失，客户端甚至还不知道这个 ID，因此它无法单独解决重复提交。

MCP 可以传递这些参数，去重语义仍要由业务服务落实。

## 一次成功返回，能证明多少事情

一个很小的实验分离了执行成功与结果正确。输入只有三个词：

```text
apple banana apple
```

独立验证器逐词检查位置，确认 `apple` 出现在第 1 和第 3 个位置，真值为 2。随后通过课程代码解释器执行两个程序：一个直接打印错误答案 3，另一个计算并打印 2。

| 程序结果 | 退出码 | 工具 verification | 独立业务校验 |
|---|---:|---|---|
| 3 | 0 | passed | 失败 |
| 2 | 0 | passed | 通过 |

两个程序都正常结束，也都通过工具已有的检查。只有加入任务专用的验证，才能区分它们。

`verification: passed` 的可信范围取决于验证器检查了什么。它可能只检查语法、格式或执行状态。接口如果没有说明验证范围，模型容易把一个局部检查结果扩大成整体完成结论。

因此，执行结果至少涉及三个问题：请求是否获得有效响应，操作是否完成，任务目标是否达到。它们可能分别得到不同答案。

## 协作工具传递任务，也传递验收责任

子 Agent 扩展了主 Agent 可用的上下文、工具和并行处理能力。独立任务可以同时进行，不同子 Agent 也可以承担不同角色，例如检索资料、检查实现和验证实验结果。

委派时，主 Agent 需要提供目标、输入、限制和验收条件。子 Agent 返回的内容则应包括产物、方法、证据和未解决的问题。

“词频已经检查，结果正确”是一句无法复核的报告。更有用的结果会说明输入文件版本、分词规则、计算结果和对应位置。对于大文件，可以返回可读取的引用、版本或哈希，以及相关片段，无需把全部数据重新复制进主 Agent 上下文。

独立验证也应避免与生产过程共享同一个明显盲区。

如果生产者和审核者都从同一份错误摘要推导结论，两者一致并不能提供多少新增证据。读取原始输入、使用独立计算路径或检查实际产物，才能增加验证的信息量。

协作还有生命周期问题。发出取消消息，只证明请求已经发送。若要报告任务停止，需要确认子 Agent 状态以及它管理的进程、远端作业是否按约定结束。消息轨迹与实际状态需要交叉核对。

这些是我们在讨论中形成的协作设计原则。

## 工具接口是模型的操作面板

模型选择工具时，通常依赖名称、描述、参数结构和当前上下文。接口中的模糊之处会变成推断负担。

比较两个定义：

```text
run(data: string)
```

```text
start_experiment(
    config_path: string,
    dry_run: boolean = true
)
```

第一个定义没有说明 `data` 是文件路径、配置内容还是命令。
第二个定义明确了动作对象和输入形式。
如果描述进一步规定 `dry_run=true` 只检查配置、不创建实验进程，模型就能够组织先校验、再启动的工作流。

描述中的承诺必须由实现兑现。校验与正式启动之间，配置可能改变，资源可能被占用。正式执行仍应检查权限和资源；需要绑定同一份配置时，可以核对内容哈希或版本。

返回接口同样影响决策。一个顶层 `success: true` 可能意味着配置有效、请求入队、进程启动，甚至整个实验完成。我们讨论了用互斥结果替代这个模糊布尔值：

```text
validation_passed
validation_failed
queued
started
start_failed
```

每个分支携带对应字段。`queued` 返回任务标识和查询入口；`started` 返回已启动运行的信息。Schema 可以约束字段组合，避免同时出现互相矛盾的状态。状态转换是否真实，仍需实现和证据保证。

专用工具也有取舍。固定实验启动器更容易约束脚本入口、配置范围和资源上限。通用代码执行器则能处理事先没有封装的任务，避免工具数量不断增长。选择取决于权限需求、参数复杂度、操作频率和模型能力。把每个底层 API 都包装成独立工具，同样可能增加模型的选择与编排负担。

## MCP 统一连接方式

当多个 Agent 应用需要连接多个工具服务时，逐对适配会形成重复工作。MCP 提供共同的协议，使服务端能够用标准形式暴露能力，由兼容客户端发现和调用。

在本次实验使用的协议版本中，结构包含 Host、Client 和 Server。Host 承载模型与应用逻辑，管理权限、连接和上下文；Client 负责与特定 Server 建立会话并交换协议消息；Server 暴露工具、资源与提示模板，可以运行在本地进程，也可以作为远端服务。[MCP 架构规范](https://modelcontextprotocol.io/specification/2025-11-25/architecture)

```text
Host：模型、上下文、权限与编排
  ├─ Client A ↔ Server A
  └─ Client B ↔ Server B
```

标准协议减少接入层差异，但业务含义仍由服务定义。客户端能理解 `tools/call` 的结构，不代表它天然知道某个实验何时算成功。权限、资源配额、幂等、业务错误和验收规则，都需要另外实现。

MCP 的三种能力也需要与前面的五类作用区分。

| MCP 能力 | 提供什么 | 示例 |
|---|---|---|
| Tools | 可调用的操作 | `run_job`、`search_logs` |
| Resources | 由 URI 标识、可读取的上下文 | `logs://runs/42` |
| Prompts | 可复用、可带参数的提示模板 | 失败诊断流程模板 |

Tools 使用 `tools/list` 发现，通过 `tools/call` 调用。只读搜索也可以作为 Tool，因此 MCP Tool 与执行类工具没有一一对应关系。[Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

Resource URI 提供内容的位置。取得 URI 后，还需要通过 `resources/read` 等接口读取，才能把内容作为证据。同一份日志也可以由读取工具返回，具体取决于服务器选择的接口。[Resources 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)

Prompt 提供可复用的消息模板，例如要求先确认运行编号，再检查首个异常，再核对退出状态。取得模板不会自动完成这些步骤，后续执行仍由应用与 Agent 组织。[Prompts 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts)

Skill 则处于另一个组织层面：它可以把知识、流程和脚本打包，指导 Agent 使用工具。它不属于上述三种 MCP 原语。

## 工具太多时，先发现，再加载

Server 提供 1000 个工具，并不要求模型每轮都看到 1000 份完整定义。Client 掌握的能力目录与模型当前上下文可以不同。

可以先让模型看到简短目录或一个搜索入口。模型根据任务查询相关能力，Host 再加载候选工具的完整 schema。工具执行产生的大量中间数据，也可以保留在运行环境中，只把必要结果送回上下文。

协议层发现 Server 暴露了什么，应用层决定当前任务向模型披露什么。MCP 标准化前者的接口，后者仍需要 Host 的选择策略。

发现本身也会失败。别名、命名空间、分页、权限过滤和过期索引，都可能让搜索返回空结果。因此，“本次没有找到”只能支持有限结论。取得 schema 后，还要继续确认权限、后端状态以及当前请求能否执行。

目录条目、接口定义和成功完成的调用，分别提供不同强度的证据。

第一组实验直接调用课程工具实现，验证了合法 Python 文件写入、错误语法拒绝、越界路径拒绝、词频程序执行，以及长输出截断与保存。五项检查全部通过。错误语法文件和越界目标均未生成，词频输出符合预期。

| 检查 | 观测结果 |
|---|---|
| 合法 Python 文件写入 | 成功，语法验证通过 |
| 含语法错误的 Python 文件 | 拒绝写入，文件不存在 |
| 越出工作区的目标路径 | 拒绝写入，目标文件不存在 |
| 词频程序执行 | 输出 apple 为 2、banana 为 1 |
| 1000 行输出处理 | 上下文返回 102 行，完整保存 1000 行 |


第二组是前文的错误答案对照，证明正常退出与工具检查通过仍可能伴随业务错误。这个小实验给验收增加了独立基准。

第三组使用 MCP Client 通过 stdio 启动课程 Server，完成初始化、工具发现和 `file_write` 调用，再直接从磁盘读取文件核对。Server 返回 12 个工具，实际取得了写文件工具的 schema，写入内容与预期完全一致。协商的协议版本为 `2025-11-25`。

环境准备中出现了一个可复现的兼容问题：课程依赖声明只有 `mcp>=0.9.0`，本次安装得到的 2.3.0 SDK 不支持课程使用的 `Server.list_tools()` 接口，Server 在握手前退出。改用 1.30.0 并补齐依赖后，通信路径跑通。这个结果说明该课程版本与这两个 SDK 版本的兼容情况，不能推广为所有 MCP 服务的兼容结论。

第四组对审批路径做故障注入。我们让审批客户端初始化抛出模拟超时，沿用课程原始异常处理与执行门控；底层动作只创建无害标记文件。另设模拟放行的正向对照，检查执行路径确实可运行。

| 场景 | 审批尝试 | 执行器调用 | 标记文件 |
|---|---:|---:|---|
| 模拟审批超时 | 1 | 0 | 不存在 |
| 模拟审批放行 | 1 | 1 | 存在 |

调用计数与外部文件状态共同支持：这条审批异常路径阻止了执行。正向对照排除了“执行器本来就不能工作”的解释。

实验还展示了字符串检测的局限。危险关键词仅出现在 Shell 注释中，也触发了审批。这说明检测器存在误报案例。

这些小实验反复指向同一条工程约束：工具需要把发生过的事情表达清楚。`queued` 应有受理记录，`started` 应有运行证据，`stopped` 应有终态确认，`verification: passed` 应有明确的检查范围。Agent 获得这些可核对的事实，才有条件把下一步动作建立在现实状态上。

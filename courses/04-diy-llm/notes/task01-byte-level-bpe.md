# DIY-LLM Task 1：字节级 BPE 分词器学习笔记

## 1. 学习目标与边界

本笔记整理字节级 BPE 分词器的核心机制，以及从“能运行”走向“可用于训练”的工程要求。

Task 1 的挑战内容必须建立在基础教程、必做代码、测试和打卡材料均完成的前提上。挑战优化不能替代基础实现。

核心目标：

1. 任意合法 UTF-8 文本可编码、可逆解码；
2. BPE 合并不跨越预分词边界；
3. 特殊 token 可以原子化处理；
4. 训练结果可复现、可序列化；
5. 优化版训练器在保持与朴素版等价的前提下减少重复扫描。

## 2. 为什么从字节开始

Unicode 字符并不是固定长度的字节序列。若直接把“字符”当作最小 token，面对罕见字符、emoji、组合字符和未知语言时，词表覆盖会变得复杂。

字节级 BPE 的做法是：

    文本
      -> UTF-8 编码
      -> 0 到 255 的单字节初始词表
      -> 学习高频字节对的合并规则
      -> token id 序列

初始词表固定包含 256 个单字节 token，因此任意 UTF-8 文本都能退化为字节序列表示。BPE 的作用不是保证“能表示”，而是把常见的字节模式合并成更长 token，从而减少序列长度。

## 3. 预分词边界与特殊 token

预分词器先将文本切成若干块，例如连续字母、连续数字、标点/emoji 和空白。一个可作为起点的 Unicode 模式是：

    \p{L}+|\p{N}+|[^\p{L}\p{N}\s]+|\s+

最重要的不变量是：BPE pair 统计与 merge 都只能在同一个预分词块内发生。否则模型会把词与词之间的空格、标点甚至特殊标记意外合并，降低分词行为的可解释性和可控性。

特殊 token 的处理顺序应为：

    原始文本
      -> 最长优先识别并隔离允许的特殊 token
      -> 对普通片段执行预分词和 BPE
      -> 将特殊 token id 与普通 token id 拼接

最长优先避免一个更长的特殊 token 被拆成多个短 token。是否允许特殊 token 还应由编码接口显式控制，避免普通文本中的相同字符串被无意解释为控制标记。

## 4. BPE 训练与编码

### 4.1 训练

初始时，每个预分词块被表示为字节 token 序列。每一轮：

1. 统计块内相邻 pair 的频率；
2. 选择频率最高的 pair；
3. 频率并列时按确定性规则打破平局，例如 token id 的字典序；
4. 将该 pair 合并成一个新 token；
5. 记录该 pair 的 merge rank；
6. 重复到达到目标词表大小或无可合并 pair。

merge rank 不是训练时临时信息，而是 tokenizer 定义的一部分。保存后的 tokenizer 必须拥有相同的 merge 顺序，才能在加载后得到一致的编码结果。

### 4.2 编码

编码阶段不能重新按当前频率决定合并，而应严格按训练得到的 merge rank 应用规则。这样训练语料以外的文本也有稳定、可复现的行为。

可以把编码理解为：对一个块中的候选相邻 pair，优先合并 rank 最小的合法 pair，直到不再存在可合并 pair。

### 4.3 解码

正确的字节级解码流程是：

    token ids
      -> 拼回每个 token 对应的字节序列
      -> 一次性 UTF-8 解码
      -> 原始文本

不能逐 token 单独 UTF-8 解码再拼接，因为一个 Unicode 字符的 UTF-8 字节可能被切在多个 token 中间。逐 token 解码会破坏多字节字符的可逆性。

## 5. 正确性不变量

一个可靠实现至少要满足以下性质：

1. 对任意合法 UTF-8 输入 x，decode(encode(x)) 等于 x；
2. 保存再加载后，词表、merge 列表、特殊 token id 与编码结果不变；
3. 固定语料顺序和 tie-break 规则时，多次训练得到完全相同的 merge 顺序；
4. 任何 merge 都不会穿过预分词块边界；
5. 禁用特殊 token 时，其文本形式按普通字节文本处理；
6. 未在训练语料出现的 Unicode 字符仍可经字节回退编码和解码。

建议测试覆盖空字符串、ASCII、中文、组合音标、emoji、连续空白、换行、特殊 token 相邻出现及未见字符。

## 6. 朴素训练与增量训练

### 6.1 朴素版本

最直观的版本在每次 merge 后重新扫描所有块，重新统计所有 pair。它便于验证正确性，但随着语料、词表和 merge 轮数增长，会反复做大量已经无效的工作。

### 6.2 增量版本

优化版的关键思想是“只更新受本次 merge 影响的局部邻居”：

1. 用可删除、可替换的节点表示一个预分词块中的 token；
2. 合并某个相邻 pair 后，只更新合并位置左右相邻的 pair 频次；
3. 用最大堆维护候选 pair；
4. 堆条目携带版本号或频次快照，实现惰性删除；
5. 弹出堆顶时再次检查其频次是否仍有效，失效条目直接丢弃。

堆和局部索引会增加实现复杂度及额外内存，因此性能报告不能只展示速度，还应同时比较峰值内存、训练语料规模和最终 merge 是否与朴素版本完全一致。

## 7. 复杂度直觉

朴素方案每轮需要接近全量扫描，整体成本会随 merge 次数重复累积。增量方案仍需要处理所有真实发生的合并，但 pair 统计变化局限在局部邻域，候选选择可由堆加速。

优化是否值得，必须通过实验回答：

- naive 与 optimized 是否逐轮选择同一个 merge；
- 同词表大小下最终编码是否一致；
- 在 1 MB、10 MB、100 MB 等规模上，训练时间如何变化；
- 峰值 RSS 或进程内存如何变化；
- 编码吞吐、平均 bytes/token、P95 序列长度是否保持可接受。

## 8. 序列化接口

建议提供以下接口：

    train(texts, vocab_size, special_tokens)
    encode(text, allowed_special)
    decode(ids)
    save(path)
    load(path)

序列化内容至少应包括：版本号、基础字节词表、merge 列表、特殊 token 映射、预分词配置和 tie-break 配置。任意字节 token 可以用整数数组或 base64 形式保存，避免直接把原始字节当作文本导致编码歧义。

## 9. 易错点

1. 把 token 长度或当前 pair 频率当作编码优先级，而不是使用固定 merge rank；
2. 允许跨空白、标点或预分词块合并；
3. 对每个 token 单独做 UTF-8 解码；
4. 忽略并列频率的确定性 tie-break，导致不同运行得到不同词表；
5. 只报告 optimized 速度，不证明它与朴素基线等价；
6. 将特殊 token 作为普通文本简单替换，导致嵌套、相邻或禁用场景出错；
7. 只测英文，忽略中文、emoji、组合字符和连续空白。

## 10. 自测清单

    [ ] 能解释 byte fallback 为什么保证覆盖任意 UTF-8 文本
    [ ] 能说明为什么 BPE merge 不应跨预分词边界
    [ ] 能区分训练期 pair 频率与编码期 merge rank
    [ ] 能说明为什么解码必须先拼字节、再整体 UTF-8 解码
    [ ] 能写出朴素与增量 pair 统计的主要差别
    [ ] 能设计 save/load、一致性与 property-based 测试
    [ ] 能用吞吐、压缩率和峰值内存评价 tokenizer

## 11. 一句话总结

字节级 BPE 用 256 个基础字节保证覆盖，用预分词边界约束合并范围，用固定 merge rank 保证编码一致性；工程上最重要的是先以朴素版本证明正确，再以等价性测试证明优化没有改变 tokenizer 的定义。

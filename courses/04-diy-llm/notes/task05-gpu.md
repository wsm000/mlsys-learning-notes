## 一、这次学习解决了什么问题

这一讲把“模型代码能运行”和“模型代码运行得高效”连接起来。大模型训练和推理并不只是执行矩阵乘法，还受到以下因素的共同限制：

- GPU 的并行执行方式；
- 显存层次和显存带宽；
- 算子访问数据的方式；
- 中间结果是否反复写回显存；
- 模型精度、激活值和 KV Cache 的存储量。

最重要的认识是：很多大模型算子不是计算单元不够快，而是数据从 HBM 搬到计算核心的速度跟不上。

## 二、GPU 并行模型

以向量加法为例：

```cpp
c[i] = a[i] + b[i];
```

不同的 `i` 之间没有数据依赖，因此可以把不同元素分给不同线程。线程通过下面的公式得到全局下标：

```cpp
i = blockIdx.x * blockDim.x + threadIdx.x;
```

例如 `N = 1000`、每个 Block 有 `256` 个线程时，需要：

```text
ceil(1000 / 256) = 4 个 Block
```

总共启动 `1024` 个线程，最后有 `24` 个线程对应 `i = 1000 ... 1023`。这些线程必须通过边界判断退出：

```cpp
if (i < N) {
    c[i] = a[i] + b[i];
}
```

这让我理解了一个容易忽略的事实：向上取整启动完整 Block 是正常做法，多余线程不是错误，真正重要的是不能越界访问。

一个 Block 有 `256` 个线程、一个 Warp 有 `32` 个线程时：

```text
256 / 32 = 8 个 Warp
```

最后一个 Warp 同时包含有效线程和越界线程。由于 Warp 中的线程共享指令流，硬件会使用 mask 屏蔽无效 lane。若同一 Warp 中不同线程进入不同分支，就会发生分支发散，路径通常需要依次执行，造成执行槽位浪费。

## 三、合并访存

相邻线程最好访问相邻地址：

```cpp
a[threadIdx.x]
```

此时一个 Warp 中的访问类似于：

```text
thread 0 -> a[0]
thread 1 -> a[1]
...
thread 31 -> a[31]
```

硬件更容易把这些访问合并成较少的内存事务。

相反：

```cpp
a[threadIdx.x * 32]
```

会产生：

```text
thread 0 -> a[0]
thread 1 -> a[32]
thread 2 -> a[64]
...
```

虽然地址有规律，但相邻线程访问的地址并不连续，属于步长较大的分散访存，带宽利用率通常更差。

这次学习中最直接的纠错是：**地址有规律不等于合并访存，关键要看相邻线程是否访问相邻地址。**

## 四、内存层次与数据复用

按照本讲的简化排序，访问速度从快到慢大致是：

```text
寄存器 -> 共享内存 / L1 -> L2 Cache -> HBM
```

越靠近计算核心的存储越快，但容量越小。GPU 优化的常见思路是：

```text
从 HBM 搬入一次
-> 在寄存器或共享内存中重复使用
-> 最后再写回 HBM
```

矩阵乘法中的 Tiling 就利用了这一点：把 `A`、`B` 的子块搬到共享内存，让多个线程复用，减少反复从 HBM 读取相同数据。输出 `C` 的部分和可以暂存在寄存器中，完成后再写回显存。

## 五、Roofline 与内存墙

对于一次 Vector Add：

```text
c[i] = a[i] + b[i]
```

每个元素大致需要读取 `4 + 4` 字节、写入 `4` 字节，并执行 `1` 次 FLOP，因此算术强度是：

```text
Arithmetic Intensity = 1 FLOP / 12 Byte
                     ≈ 0.083 FLOP/Byte
```

假设 GPU 显存带宽为 `2 TB/s`，峰值计算能力为 `20 TFLOP/s`，则：

```text
显存带宽折算上限 = 2 × 1/12
                 ≈ 0.167 TFLOP/s
```

Roofline 上限为：

```text
min(20, 0.167) = 0.167 TFLOP/s
```

所以 Vector Add 是典型的 **memory-bound** 任务。这里的 `0.167 TFLOP/s` 不是 GPU 的真实计算峰值，而是这个低算术强度任务在显存带宽约束下的有效性能上限。

## 六、六种优化技术的对应关系

| 问题 | 合适的优化 | 核心原因 |
| --- | --- | --- |
| 相邻线程访问分散地址 | 合并访存 | 减少内存事务，提高带宽利用率 |
| 多个逐元素 Kernel 产生中间结果 | 算子融合 | 减少中间结果的 HBM 往返 |
| 激活值占满显存但还有计算余量 | 重计算 | 用额外计算换显存 |
| 多个线程反复读取相同数据 | 分块 | 把数据搬入共享内存后复用 |
| 权重占用太大 | 低精度 | 减少每个元素的字节数 |
| Warp 内线程走不同路径 | 减少分支发散 | 避免分支路径串行化 |

### 1. 算子融合

例如：

```python
y = x * 2
z = y + 1
```

两个独立 Kernel 需要把 `y` 写回 HBM，再读回来。融合后可以在寄存器中连续完成计算：

```text
读 x -> 计算 x*2 -> 计算 +1 -> 写 z
```

FLOPs 大体没有减少，但访问字节数下降，算术强度提高。

Fusion 也不是一定更快。融合过度可能增加寄存器压力，导致寄存器 spill 或 occupancy 下降。因此要比较：

```text
减少的 HBM 流量
vs.
增加的寄存器、共享内存和并发度代价
```

### 2. 重计算

训练时，如果把所有激活值保存下来，会占用大量显存。梯度检查点等方法只保存部分激活，反向传播时重新执行前向计算。

本质是：

```text
用计算换显存
```

适用前提是显存紧张，而计算资源仍有余量。

### 3. 低精度

FP32 每个元素约占 `4` 字节，FP16/BF16 约占 `2` 字节，因此存储量大致减半。对于 memory-bound 算子，减少数据量可能带来收益，但不能保证实际速度正好变成 `2` 倍，因为还会受到带宽利用率、数据转换、Kernel 启动和硬件低精度支持等因素影响。

## 七、FlashAttention 与 PagedAttention

### FlashAttention：优化“怎么算”

普通 Attention 会显式生成 `N × N` 的注意力矩阵。当序列长度从 `2K` 增加到 `4K` 时，矩阵元素数量增加为原来的 `4` 倍。

FlashAttention 使用分块和 online softmax，把局部数据搬到更快的片上存储中完成计算，避免完整物化和反复读写 `N × N` 矩阵。

它的关键不是减少 Attention 的理论计算量，而是减少 HBM 访问：

```text
普通 Attention：先写出大矩阵，再反复读写
FlashAttention：分块计算，尽量在片上复用
```

FlashAttention 是精确算法，不是通过牺牲精度换速度。

### PagedAttention：优化“怎么存”

自回归推理会不断增长 KV Cache。如果为每个请求预留最大长度，会造成大量未使用空间。PagedAttention 把 KV Cache 切成固定大小的页，并通过类似页表的映射，让逻辑上连续的 KV Cache 对应到物理上不连续的显存块。

例如每页 16 tokens、请求实际生成 100 tokens：

```text
页数 = ceil(100 / 16) = 7
分配位置 = 7 × 16 = 112
浪费 = 112 - 100 = 12 个位置
```

所以：

```text
FlashAttention：减少 Attention 的显存搬运
PagedAttention：减少 KV Cache 的分配浪费
```

## 八、这次学习中的错误与修正

1. **把 `ceil(1000 / 256)` 误算成 8**
   - 修正：需要 4 个 Block，因为 `3 × 256 = 768` 不够覆盖 1000 个元素。

2. **误以为 `a[threadIdx.x * 32]` 访问位置“有规律”，所以更快**
   - 修正：合并访存看的是相邻线程访问相邻地址；步长为 32 会造成分散访存。

3. **认为 FlashAttention 主要减少计算量**
   - 修正：它主要减少 HBM 的读写和 `N × N` 矩阵的显式物化，核心计算并没有因此消失。

4. **认为 Tiling 不能保存 `A`、`B`，因为还要保存 `C`**
   - 修正：`A`、`B` 的 tile 可以放入共享内存，`C` 的部分和可以放在寄存器或共享内存中，最后再写回 HBM。

5. **把 Fusion 的收益理解成只减少 Kernel 启动次数**
   - 修正：对 memory-bound 算子，更重要的收益是减少中间结果的显存写回和重新读取。

## 九、最终总结

这一讲最重要的不是背住 GPU 的术语，而是建立一套分析顺序：

```text
先看并行性
-> 再看线程访问是否合并
-> 再算算术强度
-> 判断是 compute-bound 还是 memory-bound
-> 再选择 Fusion、Tiling、低精度或重计算
-> 最后检查寄存器、共享内存和 occupancy 的代价
```

我目前形成的三条核心判断是：

1. **GPU 擅长大量独立、相似、可并行的计算。**
2. **大模型优化经常是在优化数据搬运，而不只是优化 FLOPs。**
3. **任何优化都要同时看收益和资源代价，减少显存访问不代表一定提升端到端性能。**

本次心得记录的是基于课程材料的推导与理解，不包含真实 GPU benchmark 结果；实际性能仍需在目标硬件、框架和输入规模上测量验证。

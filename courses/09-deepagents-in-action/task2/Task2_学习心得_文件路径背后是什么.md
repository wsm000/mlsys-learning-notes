# 文件路径背后是什么？——Deep Agents 虚拟文件系统学习心得

> Task2 · 第 3 章 · 2026-10-15
>
> 本文沿着“文件在哪里、怎样留下来、如何证明正确、为什么能节省上下文”展开。实验在 vm-60 上进行；真实模型实验和脚本模型机制实验分别标注。

## 从一句“保存成功”开始

假设 Agent 告诉我们：“报告已保存到 `/reports/result.md`。”

很容易想象，电脑上出现了一个文件夹，里面躺着报告。但这句话省略了最重要的信息：它通过什么 Backend 保存？

虚拟文件系统很容易被解读成“模型能够读写文件”。这个理解没错，却还没有触及核心。这里其实有三层：

```text
write_file / read_file / edit_file  ← 做什么
            /reports/result.md   ← 操作哪个文件
                   Backend       ← 到哪里存取
```

路径像一个坐标。只有坐标，没有坐标系，我们还不知道它指向哪里。

配置 `FilesystemBackend(root_dir=某目录, virtual_mode=True)` 后，虚拟路径 `/reports/result.md` 才会映射到这个根目录里的 `reports/result.md`。两名 Agent 使用相同虚拟路径，但根目录不同，操作的就是两份文件。这里讨论的是路径映射，不能把它等同于完整的操作系统沙箱。

这个区分引出了第一个问题：读回成功，是否足以证明文件已经落盘？

## 同一个路径，可以通向两种存储

想象工具接口背后有一个可以更换的存储部件。换成 FilesystemBackend，它从磁盘读文件；换成 StateBackend，它从 Agent 的显式文件状态中取内容。

```text
                       ┌─ StateBackend ────── files 状态
/reports/raw.md ────────┤
                       └─ FilesystemBackend ─ 磁盘文件
```

因此，统一接口意味着操作方式可以相同，不意味着两边数据自动共享。StateBackend 也不会因为磁盘恰好有同名文件，就自动把它读进状态。

我们用相同内容、相同虚拟路径，在独立进程中做了对照。为了研究存储机制，实验使用脚本模型指定工具调用，真实 Deep Agents 框架负责执行；没有依赖远端模型，也没有配置 Checkpointer。

| 新进程的条件 | 实验结果 |
|---|---|
| StateBackend，不传旧文件状态 | 返回 `File not found` |
| StateBackend，通过 `files` 字段传入旧文件状态 | 成功读回 |
| FilesystemBackend，沿用原磁盘根目录 | 成功读回 |

两个写入阶段和三个读取阶段共用了五个不同 PID。成功读回的内容与写入内容一致，哈希也相同。[对照原始记录](task2-evidence/task2-backend-compare-20261015T074342Z/summary.json)

对 StateBackend，关键是有没有接回文件状态；对 FilesystemBackend，关键是文件是否还在、路径映射是否正确。

State 的恢复实验中，确实出现了一个 JSON 文件。但它是实验程序显式导出、加载的，不是 StateBackend 自动落盘。观察到数据能恢复，还要追问：到底是谁保存了它？

## 把抽象的文件变成可以打开的产物

最初的机制实验完成了：

```text
写入 → 读回 → 修改第一行 → 再读回 → 新进程读回
```

修改后的真实磁盘内容是：

```text
Agent 任务已核验完成
结果已保存至报告文件
```

这一轮由脚本模型驱动真实文件工具。它证明了工具与后端的行为，不能证明真实模型会自主选择正确操作。我随后在 vm-60 用 `cat` 打开文件，亲手确认了产物，而不只是看 Agent 的回答。[机制实验记录](task2-evidence/实验记录.md)

另一次成功实验采用程序精确写入，真实 Agent 分别读回原始资料、报告和原始资料。程序核验 UTF-8 字节与预期一致，并检查生成报告没有改变原始资料。这轮验证的是“程序写入与 Agent 读取可以访问同一存储”，不能算 Agent 自主写入成功。[该轮完整轨迹](task2-evidence/task2-deterministic-20261015T072538Z/trace.json)

FilesystemBackend 并不在意文件是谁创建的。它关心的是：当前路径能否访问到那个文件。这让已有资料可以直接成为 Agent 的工作材料。

## 为什么“成功”还需要第二层解释

接下来，我们提出严格要求：保存两行文字，再读回，生成三行报告，最后确认原始资料不变。

真实模型执行时暴露了两个细节：它把两次读取请求放在同一轮发出；它还省略了文件最后的换行。后者违反了实验脚本补充的“末行也有 LF”标准，但原始自然语言要求没有完全明确这一细节，因此也提醒我：验收标准必须先说清楚。[真实模型四步记录](task2-evidence/task2-real-four-steps-20261015-01/trace.json)

两行文字在终端看起来可能一样，字节却不同：

```text
"第一行\n第二行"     ≠     "第一行\n第二行\n"
```

如果要求逐字节一致，就需要程序读取实际字节比较，而不是让模型凭展示文本判断。

校验通过才进入下一阶段。

这也区分了两种控制：运行结束后审计 Trace，可以发现违规；在每一步之间设置检查，才能阻止错误继续传播。若要进一步限制重复写入，还应把保存与只读验收分阶段，并实际限制可用工具。
## 文件正确保存，不代表报告正确

我们给真实 Agent 一份简单资料：

```text
第1天：100
第2天：110
第3天：105
```

第 3 天相较第 1 天的涨幅可以独立计算：

\[
\frac{105-100}{100}\times100\%=5\%.
\]

第 3 天低于第 2 天，并不与整体上涨矛盾，因为两个结论比较的区间不同。

实验中，程序保存原始资料；真实 Agent 读取 `/source.md`，生成 `/report.json`，再读回报告。最终文件记录了来源路径、比较区间、起止数值、5% 的涨幅及正确解释。我们另行取回磁盘文件，确认原始资料逐字节未变，人工复核了公式和解释。[实际报告](task2-evidence/task2-analysis-20261015T075130Z/report.json)

但 Agent 写了四次报告，才进行最终读取，所以未通过预设的“读、写一次、再读”调用序列检查。内容验收通过，不代表流程验收也通过。

四次写入均返回成功，还验证了当前环境的 `write_file` 可以覆盖同一路径。这个行为与具体版本有关，不应不加核验地推广到所有版本。

如果最后一次把 5% 写成 10%，Backend 仍可能成功保存。它负责存取，不负责数学正确性。

只打开最终文件，也看不到前三次内容。我们需要保留 Trace 中的写入参数或文件快照，再用 diff 比较。diff 是比较工具，不是历史存储。

## 让资料和结论处在同一条时间线上

即使报告今天正确，明天原始资料被覆盖，复核时仍可能出问题。

因此，每轮实验应保留自己的资料与报告：

```text
/runs/001/source.md  → /runs/001/report.md
/runs/002/source.md  → /runs/002/report.md
```

报告注明资料路径、读取位置，必要时记录版本或哈希。哈希可以检查候选资料是否一致，却不能恢复已经删除的资料，也不能证明结论正确。

这让我重新理解了自己联想到的读写锁：锁可以协调读取时的并发修改，但不能替代跨时间的版本保留。后者需要快照、版本和明确的来源关系。

## 最后回到上下文：为什么要把内容放进文件

文件系统的价值不止是“成果留下来了”。它还让大量资料可以在当前聊天之外保存，需要时再取回。

如果把一千行资料存成文件，却每轮都全文读回，模型仍要处理一千行；若历史工具返回也保留，还可能重复占用上下文。真正有用的是改变信息进入上下文的方式：

```text
保留路径与简要说明
        ↓
列目录或搜索，定位相关资料
        ↓
读取需要的片段
        ↓
形成结论，保存来源与读取位置
```

文件内容不会自动进入模型的理解。读回的内容仍占用上下文；只检索到一个文件，也不能断言其他文件没有相关信息。报告应说明依据和检索范围。

文件负责留住内容，路径帮助定位，Backend 决定存取位置；上下文工程决定此刻取回什么，独立验收决定我们凭什么相信结果。

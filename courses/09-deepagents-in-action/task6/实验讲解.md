# Task6 实验讲解：记忆写在哪，审批卡在哪

配套代码：[lab_common.py](lab_common.py)、[run_memory_lab.py](run_memory_lab.py)、[run_approval_lab.py](run_approval_lab.py)、[run_store_lab.py](run_store_lab.py)、[run_risk_lab.py](run_risk_lab.py)、[run_live_lab.py](run_live_lab.py)、[probes/](probes/)。打卡稿见 [Task6_打卡笔记.md](../Task6_打卡笔记.md)。

## 0. 开篇问题：为什么新对话就忘了？

Agent 的"记忆"分两层，很多教程第一课不讲清：

1. **对话内状态**：消息列表、工具产生的文件，都放在 LangGraph 的 **state** 里，按 `thread_id` 存进 checkpointer。同一个 thread 继续聊，状态还在——所以"同一个对话里它记得你"。
2. **对话外存储**：新对话 = 新 `thread_id`，state 从零开始。要跨对话，只能把偏好写到 state 之外：**文件**（`/memory/AGENTS.md`）或 **Store**（按 namespace）。

本轮用两组对照把这变成可复现事实（H3 vs H1/H1b），而不是口号。

## 1. 记忆：三种 backend 的分工

| backend | 文件在哪 | 跨 thread | 跨进程 | 用户隔离 | 本轮证据 |
|---|---|---|---|---|---|
| `StateBackend`（默认） | graph state | ❌ | ❌ | — | H3 |
| `FilesystemBackend` | 磁盘目录 | ✅ | ✅ | ❌（靠目录约定） | H1/H1b |
| `StoreBackend` | LangGraph Store | ✅ | ✅（store 持久化时） | ✅（namespace） | H7 |

用法骨架：

```python
agent = create_deep_agent(
    model=...,
    memory=["/memory/AGENTS.md"],          # MemoryMiddleware 启动时读文件注入 system prompt
    backend=FilesystemBackend(root_dir=...),
)
```

两个容易踩的机制（都有探针留证）：

- **MemoryMiddleware 每个 thread 只加载一次**：`before_agent` 发现 state 里已有 `memory_contents` 就跳过。thread 内改磁盘文件，同线程再 invoke 不会重新注入；**新 thread 才拿到新内容**。所以"写文件"和"生效"之间隔着一次"新对话"。
- **FilesystemBackend 不创建 root_dir**：root 不存在时 `ls("/")` 报 `path_not_found`，而 `write_file` 会顺手建目录。真实模型首跑就因为这个陷进 ls 循环（见打卡稿失败记录）。

## 2. 审批：中断发生在执行前

```python
agent = create_deep_agent(
    model=...,
    backend=...,
    checkpointer=MemorySaver(),      # 中断/恢复必须配 checkpointer
    interrupt_on={"write_file": True},   # 或 permissions 里的 interrupt 规则
)
r1 = agent.invoke({...}, {"configurable": {"thread_id": "t1"}})   # 在这里暂停
r2 = agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}),
                  {"configurable": {"thread_id": "t1"}})           # 在这里放行
```

四种决定（本轮测了三种）：

| 决定 | 效果 | 本轮 |
|---|---|---|
| `approve` | 按**原始参数**执行 | H4 / L4 |
| `reject` | **不执行**，告诉模型被拒 | H5 / L3 |
| `edit` | 按**修改后参数**执行（会重入工具再过 deny 检查） | H6 / H11 |
| `respond` | 人代替工具作答，不执行 | 未测（列入下一步） |

"执行前"的最好证据不是文档，是 L3 的调用记录：拒绝后 **delete 工具的 start 事件都没出现**——它根本没跑过。

## 3. 风险分层：把"要不要人看"变成规则

```python
permissions=[
    FilesystemPermission(operations=["read"],  paths=["/**"],        mode="allow"),
    FilesystemPermission(operations=["write"], paths=["/public/**"], mode="allow"),      # L1 低风险直行
    FilesystemPermission(operations=["write"], paths=["/drafts/**"], mode="interrupt"),  # L2 人工审批
    FilesystemPermission(operations=["write"], paths=["/secrets/**"],mode="deny"),       # L3 硬闸
]
```

- 规则按声明序求值，**first match wins**：deny 写在 interrupt 前面，重叠路径直接拒（H10b）。
- `interrupt` 会自动装 HumanInTheLoopMiddleware 并生成带 `when` 谓词的 `interrupt_on`——只对命中路径的中断，不是全工具中断。
- **边界（务必知道）**：permissions 是**工具级**闸门。直接 `backend.write()` 不受它管（H12）。审批保护的是"Agent 经工具出手"这条路。

## 5. 学余力：按风险等级分层的审批方案

全部设计、代码与实验见 [risk-tier-approval.md](risk-tier-approval.md)（设计文档）、[risk_policy.py](risk_policy.py)（策略模块）、[run_risk_scheme_lab.py](run_risk_scheme_lab.py)（26 项检查）。一页摘要：

- **分级**：L0 只读自动 / L1 public 写自动 / L2 中风险写问人（approve·edit·reject）/ L3 难撤销问人（approve·reject，不给 edit）/ L4 禁止直接拒。未分类与未知工具 fail-closed 到 L2。
- **三层执行**：路径→FilesystemPermission；决定集→interrupt_on（用户条目按工具名覆盖，实现分层收窄）；内容红线→RiskGateMiddleware（权限看不到内容）。
- **审计三类事件**：执行判定＋审批请求＋人的决定，缺一不可（被拒的调用不进执行阶段）。
- **批量读洞**：secrets 读用 interrupt 权限规则，让 SDK 自动生成批量感知谓词，无路径 grep／根目录 ls 都会触发。

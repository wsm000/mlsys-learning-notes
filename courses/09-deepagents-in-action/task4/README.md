# Task4：把一部分工作搬到另一张桌子上

> 第5章学习笔记：子 Agent、委派与上下文隔离。
> 从一个直观的问题出发，结合本次真实实验理解机制与边界。

## 工作台为什么会越来越拥挤？

想象你正在写一份研究报告。

你搜索资料，读取网页，计算指标，再把结果整理成文章。每一步都合理，但对话里渐渐堆满搜索结果、原始数据、工具返回和草稿。

为了决定下一步，Agent 真的需要一直带着所有过程吗？

项目负责人需要知道研究结论，却未必需要参加每一次资料检索。本节课的委派，就从这个区别开始。

把上下文想象成一张有限的工作台。任务刚开始时，台面只有问题；工具不断返回内容，台面就越来越拥挤。最终结论也许只有几句话，得到它的过程却可能占满整张桌子。

上一节的 Todo 给桌上放了一张清单，告诉 Agent 做到哪里了。这一节则把某一部分工作搬到另一张桌子上。

这张新桌子，就是子 Agent 的独立上下文。

## 委派究竟改变了什么？

主 Agent 发出一项自包含的任务：

```python
# 示意调用，由主 Agent 通过框架提供的 task 工具发起。
task(
    subagent_type="fixture-analyst",
    description="计算两个窗口，写出报告，返回摘要和文件路径",
)
```

子 Agent 在自己的上下文中处理工具结果、计算数据、写报告。结束后，主 Agent 收到最终回传，再继续工作。

```text
主 Agent：问题 → task 委派 ─────────────────→ 接收回传 → 读报告 → 解释
                    │                           ↑
                    └→ 子 Agent：计算 → 写报告 ──┘
                         独立的消息上下文
```

主 Agent 的工作台没有变大，计算过程也没有消失。改变的是哪些内容需要留在主 Agent 面前。

这就是上下文隔离，Context Quarantine。它首先是一种信息组织方法。

## 新同事需要怎样的任务说明？

如果你只说“帮我弄一下那个东西”，新同事很难知道你的意思。子 Agent 也一样：不能假设它自动拥有主 Agent 的整段对话。

委派描述应说明输入、目标、产物路径和验收条件。角色本身还需要明确的定义：

| 配置 | 它回答的问题 |
| --- | --- |
| `name` | 你是谁？ |
| `description` | 什么任务应该交给你？ |
| `system_prompt` | 如何工作，交付什么？ |
| `tools` | 可以使用哪些应用工具？ |

本次实验中的 `fixture-analyst` 只负责计算模拟数据的两个窗口、写报告、回传结果。主 Agent 负责协调、读回和解释。

子 Agent 使用自己的系统提示词。应用工具默认可以继承；显式提供 `tools` 时，会替换应用工具映射。框架还可能安装内置文件工具，所以“只传入一个计算工具”不等于“总共只有一个工具”。这些行为应结合实际版本核对，本次环境为 deepagents 0.7.8。

## 把过程隔离，为什么还不够？

设想子 Agent 整理完资料后说：“这是结论，顺便，这是我看过的全部原始资料。”

另一张桌子上的东西，又被整箱搬了回来。

**隔离过程，不等于精简回传。**

因此，好的委派还需要回传契约：哪些内容进入摘要，哪些细节保存为文件，主 Agent 什么时候需要读取。

我们的 Advanced 实验让同一个角色完成同一个任务，只改变最终回传要求：详细组回传完整计算结果和原始记录；精简组只回传摘要与报告路径。两组主 Agent 都继续读取同一结构的报告。

| 指标 | 详细回传 | 精简回传 |
| --- | ---: | ---: |
| task 回传字符数 | 2234 | 70 |
| 主 Agent 最后一轮输入 token | 4325 | 3373 |
| 主子累计输入与输出 token | 23086 | 20131 |
| 成功模型响应次数 | 6 | 6 |
| 工具调用次数 | 5 | 5 |

两组数值和最终解释均通过检查。这对成功样本中，回传字符减少约96.9%，主模型最后一轮输入减少约22.0%，主子累计输入加输出减少约12.8%。

为什么不是同一个比例？因为主 Agent 的输入还有系统提示词、工具定义、委派消息和读回的报告。回传只占其中一部分；子 Agent 自己也仍然需要读取、处理数据。

这里记录的是实际响应报告的 token 用量，不是账单。两组各一次成功运行，精简组曾因服务端全局限流而独立重试，缓存和运行时间也不同，因此不能推广成稳定的费用或速度收益。失败尝试的额外消耗没有计入这张成功样本表。

## 怎样看见一条原本看不见的边界？

只看最终回答，很难判断上下文是否真正隔离。所以我们加入两个教学用示踪标记：

- `PARENT_ONLY` 仅出现在主 Agent 系统提示词中，要求不转发。
- `CHILD_RAW` 仅由子 Agent 的计算工具返回。

然后检查双方实际收到的模型输入。精简组中，主提示词标记没有进入子 Agent 输入；原始工具标记进入子 Agent 后续输入，但没有进入主消息。

详细组则出现一个直观变化：子 Agent 把完整结果回传后，原始工具标记也进入了主消息。详细回传中的两段 JSON 与工具返回逐字段比较一致。

这说明独立子上下文不会自动过滤最终回传。**回传契约决定哪些资料重新越过消息边界。**

观察用追踪文件可以包含完整主子过程，但这不表示这些内容都被注入主 Agent 上下文。共享文件又是另一条边界：共用 Backend 时，双方仍可能读取同一个报告。主 Agent 主动读文件后，其内容自然会进入主上下文。

因此，上下文隔离不能直接当成文件权限隔离或安全沙箱。

## 分工正确，结论就一定正确吗？

看看实验里的两组数值：

| 窗口 | 基准均量 | 近期均量 | 量比 |
| --- | ---: | ---: | ---: |
| 3 | 1300 | 1700 | 1700 / 1300 ≈ 1.31 |
| 5 | 1000 | 1600 | 1600 / 1000 = 1.60 |

1700 大于1600，所以窗口3的近期均量更大。但窗口5相对自己的基准，增幅更大。

绝对数量更大，相对增幅却可以更小。这两个指标回答不同的问题。

早期运行中，Agent 已经完成委派、计算、写报告和读回，数字也正确，却说“绝对均量不能直接比较”。后来明确区分两种比较方式，复验才通过。

所以验收需要两把尺子：一把检查真实调用与职责边界，另一把检查数值和解释。`task` 成功返回，只能说明任务返回了，不能替我们证明结论正确。

## 任务还需要一个终点

另一次详细回传试运行里，子 Agent 成功写报告后继续重复写文件。失败快照记录到至少18次成功模型响应、15次写入调用，最后由人工停止。

之后，两组统一补上规则：写入成功后立即回传，不再调用工具，并设置执行预算。加固后的两组完成了任务。

一个好的委派，需要同时说明做什么、交付什么，以及什么时候算结束。仅增加角色，不会自动带来可靠协作。

## 如果子任务本身已经是一套工作流

有时你已有包含步骤、分支和检查规则的 LangGraph 工作流，可以通过 `CompiledSubAgent` 把它作为子任务接进来。主 Agent 面对一个可委派角色，角色内部则运行预先编排的流程；其状态与消息输入输出需要满足框架契约。

这是本节拓展方向，本次实验尚未实现。

Todo 帮助 Agent 记住进度；委派让一部分工作拥有自己的上下文；回传契约决定哪些信息回来；独立验收决定是否接受交付。

面对下一个复杂任务，可以先想一想：哪些过程必须留在主 Agent 面前，哪些只需要交回一份可靠的结果？
